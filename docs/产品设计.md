## 一页纸速览

- **产品**：线下地产桌游的电子银行，只接管钱，不接管棋盘。
- **房间**：服务端 Web 房间；所有设备浏览器打开 URL/扫码加入；房主任意设备，无需小程序。
- **身份**：房主只能是“银行-only”或“双身份”；银行只能房主当；房间身份创建时固定，游戏中不可改。
- **开局**：初始资金必填，默认 2000 M；银行-only 房主没有个人余额。
- **付款**：玩家可付玩家/银行；房主可用银行付玩家；不做审批；余额不足不能转出，但可转入。
- **工资**：只能房主以银行身份发放；单人；默认 200 M，可改；不二次确认。
- **退款**：收款方发起，全额原路退回；不需付款方确认；本质是反向转账。
- **机会卡**：实体卡为准，房主在银行控制台记录金额和来源。
- **音效**：默认只有收款人设备响；付款人和其他玩家静默看流水。
- **结算**：房主结束 → 结算中（可退款/冲正/填资产）→ 确认后只读；净资产 = 现金 + 资产估值 - 负债；银行-only 不排名。

## 1. 产品定位

### 1.1 一句话定位

Monopay 是 2–6 人线下地产桌游的“局内银行”：扫码开局、自动发币、一键收付、全员流水、终局算净资产；不碰真钱，不替代棋盘。

### 1.2 目标用户与场景

- **目标用户**：有实体大富翁/地产桌游，但嫌纸币、找零、算租、记账麻烦的年轻人、家庭和桌游吧顾客。
- **人数**：2–6 名玩家；银行-only 房主不占玩家名额。
- **时长**：单局 1–3 小时。
- **典型场景**：周末聚会、家庭游戏夜、桌游吧、公司团建。
- **设备**：每人一台手机；房主可使用手机或平板作为银行终端。

### 1.3 产品角色

Monopay 在游戏中扮演三个角色：

- **银行**：发初始资金、发工资、收税费/罚款、处理机会卡和矫正付款。
- **裁判**：记录交易、保留流水、支持冲正，但不改变实体棋盘规则。
- **账本**：展示余额、流水、资产估值和终局净资产排名。

### 1.4 差异点

它的竞品不是《大富翁》App，而是桌上的纸币、计算器和 Excel。

- 不抢棋盘戏份：骰子、棋子、地契、卡牌、面对面谈判都留在桌面。
- 不碰真钱：只有游戏币 M，不能充值、提现、兑换现金。
- 不要求每人一直看手机：只有收款人有到账提示，其他人静默看流水。
- 银行必定存在：房主必须是银行-only 或双身份，不会出现“没人管银行”。

### 1.5 不做什么

- 不做线上大富翁。
- 不做骰子、棋盘、卡牌、AI 对手。
- 不做真钱支付、充值、提现、兑换。
- 不做陌生人匹配、聊天、社区。
- 不做完整地产模拟器（MVP）。
- 不做小程序、云开发、LAN Host；v3.0 采用 Web + 自有服务器。
- 不做离线/无服务端模式（需要服务器；P1 可评估 PWA 离线壳）。

### 1.6 命名与单位

- 产品名：**Monopay**
- 中文副标：**桌游账房**
- 对外少用“大富翁银行”：前者是工具，后者容易触发商标和金融类目审核。
- UI 中银行/银行是游戏角色，不代表真实金融机构。
- 游戏币单位：**M**；不出现 ¥，不使用“充值/提现/余额兑换”等真实货币表述。

## 2. 核心原则

1. **3 步一单**：点玩家 → 输金额/选类别 → 确认；常用金额一键。
2. **手机是工具，不是第二块棋盘**：不做信息流、任务、签到；动画不超过 1 秒。
3. **银行必定存在**：房主必须是银行-only 或双身份，银行只能房主当。
4. **银行发钱由房主控制，行为由玩家矫正**：不做审批流；出错由玩家指出，房主用银行付款/收款矫正。
5. **流水是最终依据**：音效只是提醒，不能只靠声音监督。
6. **只做局内钱**：游戏币仅本局有效，不可跨局、不可购买、不可兑换现金。
7. **不透支**：余额不足不能转出，但可以转入；需要钱时先抵押/变卖/收款。

## 4. 角色与权限

### 4.1 身份表

| 身份 | 个人余额 | 个人收付 | 操作银行 | 参与排名 | 占玩家名额 |
|---|---|---|---|---|---|
| 银行-only | 无 | 不可以 | 可以 | 不参与 | 不占 |
| 双身份 | 有 | 可以 | 可以 | 参与 | 占 |

- 房主始终拥有房间管理权：创建、开始、结束、确认结算、解散、冲正、标记/取消破产。
- 银行-only 房主没有个人余额，不参与排名，但可以查看所有玩家余额和流水。
- 双身份房主既是玩家也是银行，既要参与排名，也能操作银行。
- 非房主玩家不能打开银行控制台，也不能发起“银行 → 玩家”的付款。

### 4.2 权限边界

**房主可以：**

- 创建/开始/结束/解散房间。
- 以银行身份付款给玩家。
- 以银行身份收取玩家付款。
- 在银行控制台发放工资（单人）。
- 记录机会卡、抵押/变卖、矫正等银行交易。
- 冲正交易、标记/取消破产、填写矫正原因。
- 双身份房主切换操作台：“我的账本/银行控制台”；不改变房间身份。

**玩家可以：**

- 加入房间、查看自己的余额。
- 向其他玩家付款。
- 向银行付款（税费、罚款、购买、建造等）。
- 查看全员流水。
- 作为收款方发起退款。
- 在结算时填写自己的资产估值和负债。

**玩家不可以：**

- 打开银行控制台。
- 发起“银行 → 玩家”的付款。
- 付款方发起退款；付款方只能请求收款方退款，或请房主冲正。
- 修改余额、删除流水、修改他人交易。
- 非房主玩家切换房间身份或操作台。

### 4.3 房间身份与操作台

**房间身份**在创建房间时二选一，开局后不可更改：

- **银行-only**：房主没有个人余额，不占玩家名额，不参与排名；只能操作银行。
- **双身份**：房主有个人余额，占 1 个玩家名额，参与排名；同时拥有银行操作权。

**操作台**只对双身份房主有意义：

- “我的账本”：以玩家身份付款/收款，动个人余额。
- “银行控制台”：以银行身份付款/收款，银行余额无限。
- 切换操作台只是换操作入口，不改变房间身份、余额、排名、名额，也不产生任何资金变动。
- 银行-only 房主没有“我的账本”，也没有个人余额；不能中途转为双身份。
- 双身份房主不能中途转为银行-only；不存在余额冻结/恢复、退出/恢复排名、中途补发初始资金。

每笔交易必须记录操作身份/资金来源：

- 双身份房主付款时必须选“我的钱/银行”。
- 银行控制台的交易一律记为银行。
- 银行付款给房主自己的玩家身份时，流水必须显示“银行 → 房主（玩家）”。

**通用规则**：

- 操作台切换立即生效，不需要重开房间。
- 操作台切换不写入房间事件，不影响任何交易或排名。
- 结算时只有双身份/玩家身份参与排名；银行-only 不参与。
- 银行-only 想参与排名，只能在创建房间时选双身份，不能中途转换。

### 4.4 排名规则

- 银行-only：不参与排名。
- 双身份：参与排名。
- 普通玩家：参与排名。
- 破产玩家：参与排名，净资产照算，排名中标记“破产”。
- 房间身份创建后不可改，不存在“中途切银行退出排名/切回恢复”。

### 4.5 玩家名额

- 房间最多 6 名玩家。
- 银行-only 房主不占玩家名额，例如 1 个银行-only + 6 个玩家。
- 双身份房主占 1 个玩家名额。
- MVP 不支持开局后加入新玩家；断线重连除外。
- 开局后玩家不能主动退出；只能标记破产/离线，或由房主解散房间。

### 4.6 双身份付款来源

双身份房主在付款页必须先选择操作身份/资金来源：

- **我的钱**：从个人余额扣款，按玩家付款处理；余额不足时不能转出。
- **银行**：从银行付款，按银行付款处理；银行余额无限。

UI 必须明确显示当前来源，避免拿错钱。

## 5. 房间与对局流程

### 5.1 房间状态机

```text
waiting（等待加入）
   ↓ 房主开始
playing（对局中）
   ↓ 房主结束
settling（结算中，可退款/冲正/填写资产）
   ↺ 房主返回对局（确认结算前）
   ↓ 房主确认结算
settled（已结算，只读）
```

- 房间 24 小时无活动自动过期清理。
- `settling` 期间仍可退款、冲正、矫正和填写资产；`settled` 后只能查看。
- `settling` 确认前，房主可返回 `playing`；确认结算后不可返回。
- 玩家断线不影响房间状态；服务器停止则全场暂停，恢复后重连。

### 5.2 创建房间

房主在 Web 页面创建房间；房间由服务端托管，所有设备浏览器访问。

房主创建房间时必须设置：

- **房间身份**：银行-only / 双身份（二选一，必填；默认双身份）；**开局后不可更改**。
- **初始资金**：必填，默认 2000 M，必须大于 0。
- **最大玩家数**：2–6，默认 6。
- **过起点工资**：默认 200 M，可配置；每次发放时仍可改。
- **大额二次确认阈值**：默认 1000 M，仅防误触，可关闭；工资和退款豁免。
- **交易音效**：默认开启，仅收款人播放。

余额规则固定为：**不允许负余额；余额不足不能转出，但可以转入**，不提供“允许负余额”开关。

创建成功后生成：

- 6 位数字房号。
- 房间 URL/二维码：`https://domain/r/CODE`。
- `hostToken`（存浏览器 localStorage，用于房主操作）。

### 5.3 加入房间

- 玩家用手机/平板/电脑浏览器打开房间 URL/扫码，或输入 6 位房号。
- 服务端返回 `playerToken`；不需要微信登录/openid。
- 玩家可设置局内昵称和头像。
- 同一 `playerToken` 重复加入按重连处理，不重复创建玩家。
- 超过最大玩家数时拒绝加入；房主可开启“加入需房主确认”。
- 任何设备都可以加入；任何设备也都可以开房（房主浏览器）。
- 连接失败提示：检查网络/服务器地址；刷新重试。

### 5.4 开始游戏

- 只有房主可以开始。
- 至少需要 2 名玩家（双身份房主计入，银行-only 房主不计入）。
- 开始时银行自动给所有玩家身份发放初始资金；这是本局唯一一次批量发钱。
- 每笔初始资金生成流水：`银行 → 玩家 · 初始资金`。
- 银行-only 房主不发初始资金；双身份房主发一次。
- 初始资金只发一次，重连、切换操作台、结算都不重复发。
- 房间状态变为 `playing`。

### 5.5 对局中

- 实体棋盘、骰子、地契、卡牌、谈判照常进行。
- 所有人用浏览器操作；房主切到银行模式。
- 银行付款由房主操作；玩家付款可自助发起。
- 付款前校验余额：余额不足不能转出；转入不受限制。
- 余额不足时提示“余额不足，请先收款/抵押/变卖”，不产生交易。
- 所有交易实时写入流水。
- 其他玩家静默看到流水更新，没有提示和音效。

### 5.6 断线重连

- 玩家用同一 `playerToken` + 房号重连。
- 重连后拉取房间快照：房间状态、玩家余额、最近流水；带 `lastSeq` 补缺失事件。
- 重连不重复发初始资金。
- 房主关闭浏览器不影响服务端；用 `hostToken` 重新打开即可继续。
- `hostToken` 只存在本浏览器；换浏览器/清缓存会丢失房主权限（MVP 限制；P1 加房主账号）。
- 服务器宕机/重启：所有玩家断线；服务器恢复后房间从数据库恢复，玩家重连。
- 玩家切后台/锁屏：WebSocket 可能断开；回前台重连，流水为准。

### 5.7 结束与结算

- 只有房主可以结束游戏。
- 房主结束后，房间进入 `settling`（结算中），不是立即只读。
- `settling` 期间：
  - 所有玩家填写资产估值和负债；未填默认 0。
  - 玩家可在确认结算前修改自己的估值；房主可代填/修正资产估值，并留记录。
  - 仍可退款、冲正、矫正；退款截止到房主确认结算前。
  - 房主可在确认结算前返回 `playing`，继续对局。
- 房主确认结算后，房间进入 `settled`，只读；系统快照余额并计算净资产排名。
- `settled` 后不能再付款、退款、冲正或修改资产估值；需要再修正只能新开一局或在下一版处理。
- 银行-only 房主不参与排名；破产玩家参与排名并标记“破产”。
- P1 支持“再来一局”和战报分享。

### 5.8 房间过期

- 最后活动后 24 小时过期。
- 过期房间不可再加入；服务端定时清理。
- 游戏币不跨房间、不跨局。
- 房主可随时解散房间；解散后立即只读，数据保留 24 小时后清理。
- 开局后玩家不能主动退出；只能标记破产/离线，或由房主解散房间。
- 数据在服务端 SQLite/Postgres；支持备份和手动删除。

## 6. 功能设计（MVP）

### 6.1 房间

- 创建房间（Web 房主）。
- 房间 URL/二维码 + 6 位房号加入（所有浏览器）。
- 玩家列表、房主标识、身份标识。
- 房主开始/结束/解散。
- 断线重连。
- 房间事件记录：开始、结束、返回对局、结算确认、破产标记/取消、退款、冲正、矫正。

### 6.2 开局与初始资金

- 初始资金必填，默认 2000 M。
- 银行-only 房主没有个人余额。
- 双身份房主和普通玩家每人获得初始资金。
- 初始资金只发一次；这是本局唯一一次批量发钱。
- 重连、切换操作台、结算都不重复发。
- 房间身份创建后不可改，不存在“中途转双身份补发”。

### 6.3 付款

#### 付款方向

| 方向 | 发起人 | 是否需要房主审批 | 说明 |
|---|---|---|---|
| 玩家 → 玩家 | 付款玩家 | 否 | 租金、交易、借款等 |
| 玩家 → 银行 | 付款玩家 | 否 | 税费、罚款、购买、建造 |
| 银行 → 玩家（工资） | 房主 | 否 | 银行控制台发放，单人 |
| 银行 → 玩家（开局） | 系统 | 否 | 开局批量发放一次 |
| 银行 → 玩家（机会/抵押/矫正） | 房主 | 否 | 银行操作 |

> 退款不在付款页发起，由收款方在流水详情发起，见 6.7。

#### 付款字段

- 收款人：玩家 / 银行。
- 金额：整数 M，必须大于 0；不支持小数。
- 快捷金额：10 / 50 / 100 / 200 / 500 / 上次金额。
- 类别：租金、购买、税费、罚款、机会/命运、抵押/变卖、借款、还款、交易、工资、退款、矫正、其他。工资、退款由专用入口发起，不在付款页选择；类别用于流水展示和筛选。
- 备注：可选，最多 50 字。
- 资金来源：双身份房主必选“我的钱/银行”。
- 付款方余额必须 ≥ 金额；不足时不能转出。

#### 付款交互

1. 选择收款人。
2. 输入金额，选择类别，填写备注。
3. 确认付款；展示付款前后余额；余额不足时直接提示，不能确认。
4. 普通付款金额超过阈值时二次确认；普通付款包括玩家付款和银行人工付款；开局资金、工资、退款豁免。
5. 付款成功；付款人看到成功页。
6. 收款人设备播放音效、显示到账横幅、震动。
7. 其他玩家静默更新流水。

#### 付款规则

- 默认即时到账，不要求收款人逐笔确认。
- 不支持离线付款：付款人必须在线；收款人可以离线，到账后重连查看。
- 转出前校验余额：`余额 ≥ 金额`；不足则拒绝，不允许负余额。
- 转入不校验余额：玩家收款、银行付款、工资、退款、抵押/变卖所得都可入账。
- 客户端传幂等键，防连点/重试重复扣款。
- 余额只能由云函数在数据库事务中修改。
- 付款失败要明确提示，不允许“看起来成功但没到账”。

### 6.4 收款请求（P1，不在 MVP）

> MVP 不做收款请求；以下规则保留到 P1。P1 需要接订阅消息，否则付款人不在线时收不到提醒。

用于收租、玩家间收款等场景。

- 发起人选择付款玩家、金额、类别、备注。
- 付款人收到待处理请求，可接受/拒绝。
- 发起人可取消。
- 默认 10 分钟过期。
- 接受后执行付款；拒绝/过期不产生交易。
- 收款请求不经过房主审批。
- 请求只做站内提醒，不播放到账音效；实际到账后收款人才响。

### 6.5 银行台（银行控制台）

只有房主可以打开。银行-only 房主只有银行控制台；双身份房主可在“我的账本”和“银行控制台”之间切换操作台。

功能：

- 查看所有玩家余额。
- 查看本局累计发行/回收（银行付款总额 - 银行收款总额）。
- **发工资**：选择单个玩家，金额默认 200 M、可改，类别固定“工资”；不二次确认。
- **银行付款给玩家**：机会卡、抵押/变卖、矫正、其他。
- **银行收取玩家付款**：税费、罚款、购买、建造、矫正、其他。
- **退款入口**：银行作为收款方时，从原交易发起退款（全额）；银行作为付款方时，由收款玩家在流水详情发起。
- 选择玩家、金额、类别、备注。
- 填写矫正原因。
- 查看银行交易流水。
- 冲正交易。

规则：

- 银行余额无限，不参与排名。
- 银行付款不需要审批；银行收款不需要审批。
- 玩家向银行付款时，玩家余额必须 ≥ 金额；不足则拒绝。
- 所有银行交易必须留流水。
- 本局累计发行/回收只做展示，不阻断交易；用于玩家监督银行。
- 大额二次确认只防误触，不是审批；工资、退款豁免，银行人工付款仍适用。
- 银行付款给房主自己的玩家身份时，流水要明确显示“银行 → 房主（玩家）”。
- 工资由房主在银行控制台发放；开局资金由系统在开局时自动发放；这是两类规则性付款，不走普通付款页。
- 工资发错：收款方全额退回，房主重发正确金额；收款方不退时房主可冲正。

### 6.6 机会卡

机会卡、命运卡仍使用实体卡，App 不读取、不数字化整副牌。

#### 卡面要求“银行付给玩家”

1. 玩家抽到实体卡。
2. 玩家告知房主。
3. 房主打开银行控制台。
4. 选择“银行付款给玩家”。
5. 选择收款玩家。
6. 类别选“机会/命运”。
7. 输入金额，备注可写卡面文字。
8. 确认后即时到账。
9. 流水显示：`银行 → 阿杰 200 M（机会卡）`。

#### 卡面要求“玩家付给银行”

- 玩家自己发起付款，收款人选“银行”。
- 类别选“机会/命运”或对应类别。
- 不需要房主审批。
- 玩家余额不足时不能支付；需先收款/抵押/变卖。

#### 卡面要求“付给/收取每位玩家”

- MVP：逐笔手动操作。
- P1：批量收付。

#### 设计边界

- 实体卡是唯一依据。
- App 不判断卡牌对错，只记录房主/玩家申报的金额。
- 出错由玩家指出，房主用银行付款/收款矫正。
- 抵押/变卖在 MVP 只记录银行付款金额，不登记地契，也不自动生成负债；负债由玩家在结算时填写。
- MVP 不做拍照留证；P1 可选。

### 6.7 流水与纠错

#### 流水

- 所有房间成员可见。
- 按时间倒序。
- 显示：时间、付款方、收款方、金额、类别、备注、状态。
- 支持按玩家、类别筛选。
- 点击查看详情。
- 其他玩家流水静默更新，无提示、无音效、无震动。

#### 退款

- **收款方发起**，全额原路退回；付款方不能发起退款。
- 退款本质是一次反向转账，只是类型标记为“退款”；不需要付款方确认。
- 适用范围：所有有明确收款方的交易，包括玩家↔玩家、玩家↔银行、银行→玩家。
- 不可退：开局资金、退款交易本身、冲正交易本身。
- 可退：普通付款、工资、机会卡、银行收付、矫正。
- 退款后原流水标记“已退款”，新流水关联原交易；退款和冲正都是终态，同一笔原交易只能被退款或冲正一次。
- 退款方余额不足时不能退；退款不能产生负余额，需先收款/抵押补足。
- 退款方是银行时不受余额限制；退款方是玩家时余额必须 ≥ 金额。
- 退款截止到房主确认结算前；`settled` 后不能退款。
- 付款方如果希望退回，只能请求收款方退款；收款方不退时，找房主冲正。

#### 冲正

- 只有房主可以冲正。
- 冲正必须填写原因。
- 原流水保留，状态标记“已冲正”。
- 生成一条反向流水，按原金额回退，效果等于撤销该笔交易。
- 已退款/已冲正的交易不能再冲正；退款、冲正交易本身不能再冲正。
- 冲正不能导致任何玩家负余额；如果收款方已把资金花掉，需先补足余额，不能强制扣成负数。
- 不允许删除或静默修改流水。

#### 矫正

- 房主可通过银行付款/收款修正错误。
- 类别选“矫正”，必须填写原因。
- 流水显示矫正方向：`银行 → 玩家` 或 `玩家 → 银行`。
- 矫正不是审批，不需要玩家确认；玩家通过流水监督。
- 已退款/已冲正等终态交易需要再修正时，走矫正。

### 6.8 结算

- 房主结束游戏后进入 `settling`（结算中），不是立即只读。
- 房主确认结算前可返回 `playing`；确认后进入 `settled`，只读。
- 每位玩家填写：
  - 地产/建筑估值；未填默认 0。
  - 负债；未填默认 0。
- 房主可代填/修正资产估值，并填写原因；修正记录可见。
- `settling` 期间仍可退款、冲正、矫正；退款截止到房主确认结算。
- 系统计算：
  - `净资产 = 现金 + 资产估值 - 负债`
- 银行-only 房主不参与排名。
- 双身份房主参与排名。
- 破产玩家参与排名，净资产照算，排名中标记“破产”。
- 排名展示：名次、玩家、现金、资产估值、负债、净资产、破产标记。
- 现金不会为负；资产估值和负债按玩家填写计入。
- 房主确认结算后，房间进入 `settled`，只读；余额和排名快照固定，不能再改。
- 并列净资产：并列名次。
- P1：战报分享图、再来一局。

### 6.9 音效与提示

默认规则：**只有收款人的设备发出音效和提示。**

| 角色 | 音效 | 横幅 | 震动 | 说明 |
|---|---|---|---|---|
| 收款玩家 | 有 | 有 | 有 | 默认开启，可个人关闭音效 |
| 付款玩家 | 无 | 成功页 | 无 | 只看到付款成功 |
| 其他玩家 | 无 | 无 | 无 | 流水静默更新 |
| 银行收款 | 无 | 无 | 无 | 避免房主被税费刷屏 |
| 银行付款 | 收款玩家有 | 收款玩家有 | 收款玩家有 | 银行付款给玩家，玩家到账提示 |
| 工资到账 | 收款玩家有 | 收款玩家有 | 收款玩家有 | 工资是银行付款的一种 |
| 退款到账 | 原付款人有 | 原付款人有 | 原付款人有 | 退款是反向转账，原付款人变成收款人 |

补充：

- MVP 使用统一“到账”音效；P1 可区分玩家付款/银行付款。
- 退款发起人只看到成功页，不响；原付款人作为退款收款人，正常响。
- 收款人可关闭音效，但流水仍记录。
- 浏览器后台/手机锁屏时，不能保证播放音效。
- 手机静音/音量会影响声音。
- 音效是提醒，流水才是最终依据。
- 短时间多笔到账要排队播放，避免声音重叠。
- 全房播报不做 MVP，P1 可选。

### 6.10 异常处理

- **负余额**：不允许。转出前校验余额，不足则拒绝；转入不受限制。
- **余额不足**：提示“余额不足，请先收款/抵押/变卖”；不产生交易。
- **退款/冲正时余额不足**：如果收款方已把资金花掉，退款/冲正会被拒绝；需先让该玩家收款/抵押补足，不能强制扣成负数；不设“临时负余额/强制冲正”例外。
- **破产**：MVP 提供简单标记；破产玩家不能主动付款/发起收款请求，但可以被动收款（含退款）；参与排名并标记“破产”；双身份房主保留银行操作权，但不能用银行给自己（玩家身份）付款；房主可取消破产标记，取消后恢复主动付款/发起收款请求，操作写入房间事件；资产清算 P1。
- **网络中断**：显示“网络异常，请重试”；不允许离线付款。
- **重复提交**：客户端幂等键 + 服务端校验，只成交一次。
- **房间已结算**：拒绝新付款、退款、冲正，只能查看。
- **房主掉线**：银行付款暂停；玩家间付款和玩家付银行可继续。
- **余额不一致**：以流水为准，房主可冲正/矫正；不允许删除或静默修改流水。

### 6.11 MVP 不做

- 地产登记、自动算租金。
- 棋盘、骰子、卡牌。
- 玩家交易撮合、拍卖。
- 借款/欠条/利息。
- 聊天、社区、排行榜。
- 单机模式。
- 全房音效/语音播报。
- 房主转让。
- 战报分享图、再来一局。
- 真钱支付、充值、提现、兑换。
- 收款请求（P1）。
- 部分退款（P1）。
- 负余额/透支（规则禁止，不存在开关）。
- 破产资产清算（P1）。
- 抵押/变卖的资产登记（P1；MVP 只记钱，不登记地契）。

- 银行-only 房主不显示在排名中。

### 7.3 视觉与内容风格

- 默认主题 A “奶油与钴蓝”：奶油纸卡、墨蓝字、钴蓝主色、珊瑚支出、青绿收入；去掉深绿桌布、金币、黄铜、筹码等赌场符号。
- 术语更正：游戏内机构统一称“银行”，不再使用“钱庄”；产品名保留“桌游账房”，页面标题用“我的账本 / 银行台”。
- 可切换主题 B–F：燕麦与松绿、石墨与橘、雾紫与柠檬、海盐与番茄、咖啡与电光青；同一布局只换配色，允许更大胆，但仍禁止赌场符号。
- 页面内容仍按“一屏一件事”：首页负责开桌/加入，账本负责余额与付款，银行台负责发行/回收/纠错，结算负责对账。
- 文案短、准、清楚；金额统一 `2,000 M`，不用“元/块/钱包/充值”等真钱词，也不用“下注/庄家/筹码”等赌场词。
- 品牌图标也要重做：旧“深绿底 + 金币 M”不再作为默认；新方向是纸卡/回单 + M 字标，不用金币外圈和金属高光。
- 完整规范见 [UI设计规范.md](UI设计规范.md)。[prototype/index.html](../prototype/index.html) 是旧视觉方向，仅保留页面结构参考，不作为视觉验收依据。

## 8. 关键规则汇总

| 规则 | 结论 |
|---|---|
| 初始资金 | 必填，默认 2000 M，>0；开局只发一次 |
| 工资 | 只能房主以银行发放；单人；默认 200 M，可改；不二次确认 |
| 负余额 | 不允许；余额不足不能转出，但可转入（用于抵押/收款） |
| 破产 | 简单标记；不能主动付款/发起收款请求；可被动收款；参与排名并标记；资产清算 P1 |
| 大额确认 | 普通付款默认 >1000 M 二次确认；工资、退款豁免 |
| 付款到账 | 即时到账，不要求收款人逐笔确认 |
| 收款请求 | P1；MVP 不做 |
| 退款 | 收款方发起；全额；不需付款方确认；原路退回 |
| 冲正 | 房主操作，填原因，原流水保留；已退款/已冲正不能再冲 |
| 房间过期 | 24 小时无活动 |
| 游戏币 | 仅本局有效，不跨局、不兑换 |
| 银行余额 | 无限，不参与排名 |
| 机会卡 | 实体卡为准，房主记录金额 |
| 音效 | 只有收款人响；银行收款静音；退款给原付款人响 |
| 其他玩家 | 流水静默更新，无提示/音效/震动 |

### 8.1 文案示例

- 首次进入房间：`本局仅使用游戏币 M，不可充值、提现或兑换现金。`
- 到账横幅：`银行 → 阿杰 +200 M（机会卡）`
- 付款成功：`已支付 200 M 给 小美`
- 余额不足：`余额不足，请先收款/抵押/变卖`
- 退款：`小美已退回 200 M（退款）`
- 冲正：`该交易已冲正，原因：租金金额记错`
- 结算：`净资产 = 现金 + 资产估值 - 负债`

### 9.2 索引建议

- `rooms.code`：活跃房间唯一索引。
- `rooms.expiresAt`：过期清理索引。
- `players`：`roomId + openId` 唯一索引。
- `transactions`：`roomId + createdAt` 复合索引。
- `transactions`：`roomId + clientRequestId` 唯一索引（幂等）。
- `payment_requests`：`roomId + status + createdAt` 复合索引（P1）。
- `room_events`：`roomId + createdAt` 复合索引。

### 9.3 转账事务

所有余额变动必须通过云函数 + 数据库事务：

1. 校验房间状态：付款为 `playing`；退款/冲正/矫正允许 `playing` 或 `settling`。
2. 校验操作人权限。
3. 校验金额为整数且 > 0。
4. 校验付款方状态（非破产）。
5. 转出方校验余额：玩家 `余额 ≥ 金额`；银行不校验；不足则拒绝，不允许负余额。
6. 扣减付款方余额；增加收款方余额；玩家收款不校验余额。
7. 写入 `transactions`。
8. 更新房间 `lastEventAt`。
9. 返回最新余额。

客户端不允许直接写 `players.balance`。

退款、冲正、矫正同样不能导致任何玩家负余额；余额不足时拒绝。工资和开局资金由银行付款，不校验银行余额。

> v3.0 Web 版：10.1–10.3、10.6、10.7 的云开发描述由附录 C 和 [技术路线-Web版](技术路线-Web版.md) 覆盖；云开发/LAN 方案保留为历史/备选。

### 10.1 架构（v1.0 云方案）

```text
玩家A小程序 ─┐
```

- `createRoom`

- 工资、退款豁免大额二次确认。

### 10.3 实时同步（v1.0 云方案）

- 收款人 `watch` 自己的 `user_inbox`；收到事件后播放音效/横幅/震动。
- 其他玩家不 watch，页面可见时每 2–3 秒 `getRoomSnapshot`，只静默更新流水。
- 退款到账按“收款人”处理：原付款人响，退款发起人只看到成功页。
- 冲正默认不写 inbox、不响；受影响玩家以流水为准。
- `watch` 断线时降级为 2–3 秒轮询；重连时拉取快照，避免漏消息。

### 10.4 二维码与房号

- Web 版：房间 URL `https://domain/r/CODE`，前端生成二维码。
- 6 位房号；服务端唯一；加入限流。
- 相机/微信扫一扫打开浏览器；微信内浏览器异常时提示用 Safari/Chrome。

### 10.5 音效

- 使用 HTMLAudioElement；首次点击“开启音效”解锁。
- 只有收款人客户端播放。
- 付款人和其他玩家不播放。
- 银行收款不播放。
- 工资到账由收款玩家播放。
- 退款到账由原付款人播放；退款发起人不播放。
- 冲正默认不播放；受影响玩家以流水为准。
- 浏览器后台/锁屏时无法保证播放。

### 10.6 安全（v1.0 云方案）

- 数据库权限：除 `user_inbox`（仅本人可读）外，客户端不直读；房间/流水通过云函数快照读取。
- 写操作全部走云函数。
- 房主权限在服务端校验，不能只靠前端隐藏按钮。
- 付款、退款、冲正、矫正均在服务端校验余额，不允许负余额。
- 房号加入限流，防撞库。
- 不存储手机号、通讯录、位置。
- 游戏币仅本局有效，不提供任何兑换接口。

### 10.7 成本（v1.0 云方案）

- 使用微信云开发，不需要购买服务器、域名、HTTPS 证书。
- 云开发有免费额度/体验套餐，超出后按量或套餐计费。
- 具体免费额度和价格会调整，以云开发控制台账单页为准。
- 朋友局数据量很小，早期通常在免费额度内。
- 6 人试玩的量级估算：免费额度内约 0 元/月；最低套餐约 20–70 元/月；详见《技术路线》10.5。
- 上线前设置预算提醒，避免意外用量。

### 10.8 关键实现约束（MVP 必须满足）

- 所有时间以服务端为准：`createdAt`、`expiresAt`、`settlingAt`、`settledAt` 不用客户端时间。
- 幂等：`roomId + clientRequestId` 唯一；重复请求返回原交易，不重复扣款。
- 开局发初始资金必须原子或可重试：要么单事务完成，要么逐人发放并记录 `fundedAt`，未全部完成前房间不进入 `playing`。
- 余额校验在事务内完成：玩家转出 `余额 ≥ 金额`；银行不校验；任何写入都不能产生负余额。
- 读权限：客户端不直连数据库；所有读写走 REST/WebSocket，token 校验；数据库只对服务端开放。
- 实时：WebSocket 断线重连 + 快照补偿；轮询兜底。
- 对账：每笔交易记录双方交易后余额；提供按房间重算余额的校验脚本。
- 房号加入限流；房间过期用服务端定时任务清理。

## 11. 合规与风险

### 11.1 合规边界

- 只做游戏币 M。
- 不提供充值、提现、兑换现金。
- 游戏币仅本局有效，不跨局转移。
- 不做真钱支付、商户代收代付、资金池。
- 不做与输赢挂钩的现金结算。
- 不鼓励任何形式的赌博。

### 11.2 命名与 IP

- 对外使用“Monopay 桌游账房”。
- 少用“大富翁银行”等可能涉及商标/金融类目的名称。
- “Monopay”与“Monopoly”存在近似联想，上线前做商标检索，准备备选名。
- 不使用官方大富翁棋盘、角色、卡牌、Logo 素材。
- UI 中“银行/银行”是游戏角色，不是真实金融机构。

### 11.3 类目

- 尽量按“工具/生活服务-桌游辅助工具”设计。
- 不做游戏玩法、不做虚拟货币充值，避免被要求按游戏类目审核。
- v3.0 是 Web 应用，无小程序审核；如果后续做小程序，再按类目要求。
- 上线前按微信平台规则复核类目和资质要求。

### 11.4 隐私

- 只获取用户填写的昵称/头像；不获取手机号、通讯录、位置。
- 不依赖微信 openid；使用本地随机 token。
- 提供隐私政策和数据删除说明。
- 房间数据按保留策略清理。

### 11.5 风险与应对

| 风险 | 应对 |
|---|---|
| 服务器停机/重启会暂停全场 | 进程守护/重启；每日备份；P1 房主转让 |
| 不允许负余额，玩家余额不足时无法付款/退款/冲正 | 提示先收款/抵押/变卖；MVP 只记录抵押金额，不做地契登记 |
| 音效受后台/静音影响 | 以流水为准；收款人回前台后看到账记录 |
| 服务器资源/证书到期 | 1 核 1G 足够；证书自动续期；uptime 监控 |
| WebSocket 被反代断开 | 心跳/重连；Nginx 超时配置；轮询兜底 |
| 域名/HTTPS 未就绪 | 先用 IP + HTTP 内测；正式上 HTTPS |
| 房号被猜 | 6 位随机、限流、房主确认、短时房间 |
| 手机分散注意力 | 只保留必要操作；其他玩家静默 |
| 规则版本差异 | 初始资金/工资可配置，不硬编码 |
| 范围蔓延 | 严格按 MVP 清单，地产/批量/借款放 P1 |

## 12. MVP 验收标准

### 12.1 功能

- [ ] 房主在 Web 创建房间时必须选择“银行-only/双身份”，并填写初始资金。
- [ ] 房主不能选择纯玩家身份。
- [ ] 房间身份创建后不可改；不存在中途转身份。
- [ ] 银行只能房主操作，其他玩家看不到银行控制台。
- [ ] 2–6 名玩家可用浏览器打开 URL/扫码/房号加入；银行-only 房主不占名额。
- [ ] 开始游戏后，所有玩家身份获得初始资金；银行-only 房主没有个人余额。
- [ ] 初始资金只发一次，开局后不重复发。
- [ ] 玩家可向玩家、向银行付款；余额不足时不能转出，但可转入。
- [ ] 房主可以银行身份向玩家付款、收取玩家付款。
- [ ] 房主可以在银行控制台发工资（单人，默认 200 M，可改，不二次确认）。
- [ ] 机会卡可由房主记录为银行付款/收款。
- [ ] 流水全员可见，支持筛选和详情。
- [ ] 退款由收款方发起，全额，不需付款方确认；房主可冲正并填写原因。
- [ ] 双身份房主切换操作台不改变余额、排名、名额；不重复发钱。
- [ ] 结算按“现金 + 资产估值 - 负债”计算净资产。
- [ ] 结算中可退款/冲正/填资产；确认结算后只读；确认前房主可返回 playing。
- [ ] 银行-only 房主不参与排名；双身份参与排名；破产玩家标记“破产”。
- [ ] 破产标记可取消；取消后恢复主动付款/发起收款请求。
- [ ] 付款人必须在线；收款人离线可到账，重连可查。
- [ ] 服务器宕机/重启后房间恢复；房主关闭浏览器不影响服务端。
- [ ] 银行控制台显示本局累计发行/回收。
- [ ] 断线重连后余额、流水恢复。
- [ ] 只有收款人设备播放音效/显示到账横幅/震动。
- [ ] 付款人和其他玩家无音效、无提示；流水静默更新。
- [ ] 银行收款默认静音。
- [ ] 结算确认后的房间只读，不能继续付款、退款、冲正。

### 12.2 数据一致性

- [ ] 连续 100 笔付款，余额与流水完全一致。
- [ ] 重复点击/网络重试不会重复扣款。
- [ ] 冲正后原流水保留，反向流水正确。
- [ ] 初始资金只发一次，重连不重复。

## 附录 A：MVP 自包含性与试玩计划

### A.1 MVP 自包含性：不依赖 P1/P2

本版是完整的试玩版设计。P1/P2 的功能都不阻塞 MVP；MVP 用更简单的手动/口头方式替代。

| 后续功能 | MVP 替代方案 | 是否阻塞 |
|---|---|---|
| 收款请求 | 直接付款 + 退款 + 口头提醒 | 否 |
| 部分退款 | 全额退款 + 重新付款 | 否 |
| 抵押/变卖资产登记 | 银行付款记“抵押/变卖”；负债结算时手填 | 否 |
| 破产资产清算 | 房主标记破产；结算填资产/负债 | 否 |
| 房主转让 | 服务端重启/恢复；房主用 hostToken 重连；不做云转让 | 否，但有运营风险 |
| 地产/租金自动计算 | 手动付款 | 否 |
| 批量收付 | 逐笔操作 | 否 |
| 单机/全房播报/战报 | 不做 | 否 |

结论：MVP 不依赖任何 P1/P2 功能。v3.0 的外部依赖是 **现有服务器 + HTTPS/WSS 部署**，不是产品规则依赖。

### A.2 试玩观察指标

试玩时记录以下指标，用来决定 P1 优先级：

| 指标 | 用途 |
|---|---|
| 完成一局的房间数/比例 | 判断流程是否走得通 |
| 单笔付款中位时长 | 验证“比纸币快” |
| 每局付款笔数 | 判断操作频率 |
| 余额不足被拒次数 | 判断初始资金/工资是否合理 |
| 退款次数/金额/原因 | 判断误操作率 |
| 冲正/矫正次数 | 判断记错账频率 |
| 工资发放次数/金额 | 判断规则是否符合实际 |
| 音效漏音/重复次数 | 判断提醒是否可靠 |
| 房主掉线次数/时长 | 判断单点风险 |
| 结算填写耗时/未填比例 | 判断结算体验 |
| 付款失败/重试次数 | 判断网络/交互问题 |
| 玩家主观反馈 | 是否愿意再用、是否比纸币快 |

### A.3 试玩脚本

1. 6 人局，银行-only 和双身份各跑一局。
2. 开局资金、工资、玩家付款、玩家付银行、银行付款各操作一次。
3. 余额不足：0 余额付款被拒；收到抵押/变卖款后可付；退款/冲正余额不足时先补足。
4. 退款：收款方全额退；付款方不能退；已退款不能再退；退款到账原付款人响。
5. 冲正：房主冲正；已退款不能冲；收款方花掉钱时冲正失败，补足后成功。
6. 结算：房主结束进入 settling；返回 playing；再结束；填资产；确认后只读；破产标记/取消。
7. 断线：收款人离线时，付款人仍可付款；收款人重连看到账；服务器重启后房间恢复，玩家重连。
8. 音效：只有收款人响；银行收款静音；工资到账响；退款到账原付款人响。
9. 权限：非房主看不到银行；付款方不能退款；银行-only 不排名；双身份切操作台不改变余额。
10. 异常：重复点击不重复扣款；房号错误/满员/过期；结算后拒绝付款、退款、冲正。

### A.4 试玩后的改进顺序

1. 先修“走不通/算不清/退不回”的问题，再谈新功能。
2. 如果付款太慢，优先做快捷收款人、类别可空、5 秒撤销，而不是加功能。
3. 如果余额不足/退款失败频繁，再评估是否开放部分退款或调整初始资金/工资。
4. 如果房主掉线影响大，再排房主转让或临时银行授权。
5. 地产/租金自动计算是最大的下一块，但应在 MVP 试玩确认“银行本身有人用”后再做。

## 附录 B：v2.0 局域网 Host 改造

> 历史方案：已被 v3.0 Web + 自有服务器方案取代；保留为备选/参考，不再作为当前实现依据。

### B.1 设备与房间形态

| 设备 | 角色 |
|---|---|
| Android 手机/平板 | **Host App**：开房、本地 TCP 服务、SQLite、银行控制台、二维码 |
| 笔记本/平板 | **Host App**（Node/Electron）：开发/试玩最稳；可选 |
| iPhone | **玩家小程序**：只能加入，不能开房 |
| Android 手机 | **玩家小程序**：加入、付款、流水、结算 |
| 任意手机浏览器 | **玩家回退**：小程序 LAN TCP 不可用时，Host 提供 HTTP/WS |

- 房主必须在 **Host App** 里开房；小程序创建页只做提示。
- iPhone 创建页提示：“请用非 iPhone 设备开房间”。
- Android 创建页提示：“请打开 Monopay Host App 开房”；Host App 单独安装。
- 玩家不需要装 Host App；小程序扫码/输 IP 加入。

### B.2 与 v1.0 的差异

| 项目 | v1.0 云开发 | v2.0 局域网 Host |
|---|---|---|
| 房间服务 | 微信云开发 | 房主 Host App |
| 创建房间 | 小程序 | Host App |
| 加入 | 小程序码/房号 | `tcp://IP:port?room=CODE` / 手动 IP + 房号 |
| 身份 | 微信 openid | 本地 `playerToken` / `hostToken` |
| 数据 | 云数据库 | Host 设备 SQLite |
| 实时 | 云 watch | TCP 事件 |
| 房主掉线 | 银行付款暂停，玩家付款继续 | Host 停止 = 全场暂停；重启后重连 |
| 费用 | 约 20–70 元/月 | 0 云费；Host 设备/热点/电量 |
| 审核 | 小程序类目 | 小程序 LAN TCP 审核风险；Host APK 不走微信审核 |

角色、付款、退款、冲正、结算规则不变。

### B.3 iPhone 提示

- 小程序创建页检测 `platform === 'ios'`：
  - 显示“iPhone 不能当房主，请用 Android/平板/笔记本开房间”。
  - 不显示创建按钮。
- iPhone 可以正常加入、付款、结算。
- Android 创建页显示“请打开 Monopay Host App”；Host App 未安装时给出安装说明。

### B.4 连接与数据

- Host App 显示 IP/端口/房号 + 二维码。
- 玩家小程序扫码/输 IP；`wx.createTCPSocket` 连接；NDJSON 协议。
- 同一 Wi-Fi 或房主热点；关闭 AP 隔离；Host 防火墙放行端口。
- 数据在 Host 设备 SQLite；Host 支持导出备份/手动删除。
- Host App 需要前台服务 + 唤醒锁 + 充电；否则容易掉线。
- 玩家切后台/锁屏可能断线；回前台重连，带 `lastSeq` 补事件。

### B.5 验收补充

- [ ] iPhone 创建房间页提示换非 iPhone，不显示创建按钮。
- [ ] Android/平板/笔记本 Host App 能开房并显示 IP/端口/二维码。
- [ ] 6 个玩家小程序扫码/输 IP 加入，不依赖云开发。
- [ ] Host App 停止后玩家收到明确提示；重启后能恢复房间并重连。
- [ ] Host App 能导出 SQLite/JSON 备份。
- [ ] 全程无云开发调用、无云费用。
- [ ] `wx.createTCPSocket` 在 iOS/Android 体验版真机通过 Gate 0。

### B.6 Gate 0 与回退

**Gate 0**：1–2 天验证 `wx.createTCPSocket` 连笔记本 Node TCP 服务；iOS/Android 真机；6 客户端；断线重连；扫码。

- 通过：按 [技术路线-局域网](技术路线-局域网.md) 开发 Host App + 小程序。
- 不通过：回退浏览器玩家端（Host 提供 HTTP/WS），或回退云开发小程序。
- 小程序审核不接受 LAN TCP：回退浏览器/云。

**总结：v2.0 是“零云费、房主设备当服务器、非 iPhone host、小程序玩家”的局域网方案；先过 Gate 0，再全量开发。**

## 附录 C：v3.0 Web + 自有服务器改造（当前方案）

### C.1 设备与形态

| 设备 | 角色 |
|---|---|
| 任意手机/平板/电脑浏览器 | 房主：开房、银行、流水、结算 |

| 项目 | v2.0 局域网 Host | v3.0 Web + 服务器 |

| 数据 | Host 设备 SQLite | 服务端 SQLite/Postgres |
| 审核 | 小程序 LAN TCP 风险 | 无小程序审核 |
| 部署 | Android Host App/热点 | 一个 Web 服务 + HTTPS |

### C.3 技术形态

- 前端：Vue 3 + Vite + TypeScript + Vant 4 + Tailwind CSS + Motion One；移动优先。
- UI：默认 A“桌游银行 · 奶油与钴蓝”，B–F 主题可切换；自定义余额卡、付款抽屉、数字键盘、成功动画，不直接用默认 Vant 皮肤；不用金币/黄铜/筹码等赌场符号。
- 后端：Node.js 20 + Fastify + WebSocket + Zod。
- 数据库：SQLite（MVP）或现有 Postgres/MySQL。
- 部署：现有服务器 + Nginx/Caddy + HTTPS；Docker Compose 或 systemd。
- 共享：`ledger-core` + `shared` 类型/Zod schema；规则只写一份。
- 实时：REST 命令/查询 + WebSocket 事件；断线重连 + 快照补偿。
- 二维码：房间 URL 二维码；相机/微信扫一扫打开浏览器。
- 音效：HTMLAudioElement；首次点击解锁；收款人响，其他静默。

详细见 [技术路线-Web版](技术路线-Web版.md)。

### C.4 验收补充
