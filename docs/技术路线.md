# Monopay 技术路线（MVP 试玩版）

> 历史方案：v3.0 已改为 Web + 自有服务器；本文保留为云开发备选/参考。
>
> 版本：v1.0 ｜ 日期：2026-11-01 ｜ 对应产品设计 v1.0
>
> 目标：用微信小程序 + 微信云开发，做出一个 2–6 人可真实打完一局的试玩版。
>
> 范围：只做 P0；P1/P2 不进入首版，但架构上预留扩展点。

---

## 0. 结论先行

- **客户端**：微信小程序原生 + TypeScript + TDesign Mini Program。
- **后端**：微信云开发，**一个 `api` 云函数 + 一个 `timer` 云函数**；逻辑上按用例拆分，物理上先合一个函数，减少部署和共享代码成本。
- **写链路**：所有余额变动走 `api` 云函数的数据库事务；客户端不直接写库。
- **读链路**：客户端通过 `getRoomSnapshot` / `listTransactions` 拉取；实时只给“收款人”推一条 `user_inbox`，其他玩家靠轮询/页面刷新，避免复杂权限和全量 watch。
- **账本**：`transactions` 是唯一事实源；`players.balance` 只能由事务改；每笔交易记录双方交易后余额；不允许负余额。
- **核心逻辑**：抽成纯 TypeScript 的 `ledger-core`，先用 Jest 测，再由云函数包一层数据库适配器。
- **节奏**：M0–M6，全职 5–7 周到可试玩；3 周左右可到“能付款”的可玩 demo，但试玩版需要把退款/结算/音效/断线补完。

## 1. 目标与非目标

### 1.1 目标

- 2–6 人，单局 1–3 小时，能完整走完：建房 → 加入 → 开局 → 付款/工资/退款/冲正 → 结算。
- 余额与流水强一致：任意时刻 `sum(交易) == balance`。
- 不允许负余额；余额不足时明确拒绝，玩家先收款/抵押/变卖补足。
- 收款人 1 秒内看到到账提示；其他玩家静默。
- 断线重连能恢复余额、流水、待结算状态。
- 房主掉线时，玩家间付款、玩家付银行仍可继续；银行付款暂停。

### 1.2 非目标

- 不做棋盘、骰子、卡牌、地产登记、租金自动计算。
- 不做真钱支付、充值、提现、兑换。
- 不做局域网直连、离线付款、单机模式。
- 不做收款请求、部分退款、批量收付、房主转让、破产资产清算（P1）。
- 不做多端同步的复杂冲突合并；同一账号多设备以“最后活跃设备”为 P1。

### 1.3 关键指标

| 指标 | 目标 |
|---|---|
| 单笔付款中位时长 | ≤ 8 秒 |
| 收款人到账提示 | 正常网络 ≤ 1 秒 |
| 6 人连续操作 | 无卡顿、无重复扣款 |
| 余额/流水一致 | 100 笔付款后完全一致 |
| 开局发钱 | 不出现“半开房”（部分玩家有初始资金、部分没有） |
| 崩溃恢复 | 任意一步失败可重试，不重复扣款 |

## 2. 技术选型

| 层 | 选择 | 理由 | 备选/不选 |
|---|---|---|---|
| 客户端 | 微信小程序原生 + TypeScript | 包体小、云开发集成好、审核路径短 | Taro/uni-app 跨端，但 MVP 不需要 |
| UI | TDesign Mini Program | 组件全、维护活跃、TS 友好 | Vant Weapp 也可，二选一 |
| 后端 | 微信云开发：云函数 + 云数据库 | 免运维、天然拿 openid、实时 watch | 自建 Node/Go：成本、备案、运维都更重 |
| 实时 | 云数据库 `watch` + 轮询降级 | 低延迟、无需自建 WSS | 自建 WebSocket：MVP 不值得 |
| 构建 | `tsc`（小程序）+ `esbuild`（云函数） | 快、可 CI、产物小 | gulp/webpack 更重 |
| 测试 | Jest（`ledger-core`）+ 云环境脚本 | 纯逻辑可单测；数据库一致性用脚本压 | 只靠手测不够 |
| CI | GitHub Actions 跑 lint/typecheck/test；部署先手动 | MVP 求稳 | 全自动部署可后补 |

### 2.1 关键选型说明

**为什么先合一个 `api` 云函数？**

产品文档列了十几个云函数，但 MVP 阶段拆成十几个目录会带来：

- 共享代码（校验、账本、错误码）复制或打包麻烦；
- 每个函数独立依赖、独立冷启动、独立部署；
- 权限/状态校验容易各写一套。

所以逻辑上按用例分模块，物理上先一个 `api`：

```text
api(event):
  switch event.action:
    createRoom / joinRoom / startGame / endGame / getRoomSnapshot / listInbox
    playerPay / bankPay / paySalary / bankCollect
    refundTransaction / reverseTransaction
    markBankrupt / submitAssets / confirmSettlement / resumeGame / dissolveRoom
    listTransactions / getRoomQr / logEvent
```

后续如果某个动作变重（比如结算、二维码），再拆独立函数。`timer` 单独一个，负责过期清理和限流计数清理。

**为什么实时只推收款人？**

产品要求“只有收款人响，其他玩家静默”。如果所有客户端都 watch 整个房间/流水：

- 每个客户端都要有读权限，云开发安全规则做“房间成员”判断很绕；
- 6 个客户端都收全量事件，浪费连接和流量；
- 容易把 `openId` 暴露给同房玩家。

改成 **每个玩家一条 `user_inbox`**：

- 付款事务提交时，只给收款人的 feed 追加一条事件；
- 收款人 watch 自己的 inbox，立即响；
- 其他玩家不 watch，靠 `getRoomSnapshot` 轮询/页面刷新；
- inbox 用 `ownerOpenId` 做安全规则，读不到别人的。

这既满足“1 秒到账提示”，又把权限和实时范围收窄。

## 3. 总体架构

```text
┌──────────────────────── 微信小程序 ────────────────────────┐
│ pages（首页/大厅/账房/银行/付款/流水/结算/设置）              │
│ store（roomStore / uiStore / audioStore）                    │
│ services（api.ts / realtime.ts / audio.ts / format.ts）      │
│                                                              │
│  callFunction('api', { action, payload })                    │
│  watch(user_inbox.doc(feedId))  ← 只有收款人                 │
│  setInterval(getRoomSnapshot)   ← 其他玩家/兜底              │
└──────────────────────────────┬───────────────────────────────┘
                               │ HTTPS / WSS
┌──────────────────────────────▼───────────────────────────────┐
│ 微信云开发                                                    │
│  ├─ api 云函数（路由 + 用例 + ledger-core + 权限/状态校验）   │
│  ├─ timer 云函数（房间过期、限流计数、数据清理）              │
│  ├─ 云数据库（rooms / players / transactions / ...）          │
│  └─ 云存储（二维码图片、音效可选）                            │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 一次付款的链路

```text
玩家点确认
  → 小程序 callFunction('api', { action:'playerPay', ... })
  → api 校验 openid/成员/房间状态/金额/余额
  → db.runTransaction:
       读 payer / payee / room
       扣 payer.balance，增 payee.balance
       写 transactions（含 balanceAfter、seq）
       更新 room.seq / lastEventAt
       给收款人写 user_inbox
  → 返回 transaction + 最新余额
  → 付款人看到成功页
  → 收款人 watch 到 inbox，播音效/横幅/震动
  → 其他玩家下一次轮询/刷新看到流水
```

### 3.2 一次结算的链路

```text
房主结束
  → api endGame
  → room.status = settling，endedAt/settlingAt
  → 玩家 submitAssets（资产估值/负债）
  → 房主 confirmSettlement:
       db.runTransaction:
         校验 room.status == settling
         读所有 players + asset_snapshots
         计算净资产/排名，写 settlements
         room.status = settled，快照现金
  → 只读
```

### 4.1 共享代码怎么进云函数

云函数目录各自部署，不能直接 `import` 仓库外的 TS。MVP 用 **esbuild 打包**：

```text
packages/ledger-core/src/*.ts
        ↓ esbuild bundle
cloudfunctions/api/ledger-core.js
```

`api/index.ts` 也由 esbuild 打成 CommonJS，`package.json` 只留 `wx-server-sdk`。这样：

- 本地可以跑 Jest；
- 云函数部署产物是单文件，冷启动小；
- 不需要在云函数目录里复制业务代码。

小程序端只共享**类型**，不共享运行时代码；类型可以用 `tsc --emitDeclarationOnly` 或手工维护。

### 5.2 索引

| 集合 | 索引 | 说明 |
|---|---|---|
| `rooms` | `code` 唯一 | 房号查询 |
| `rooms` | `status + expiresAt` | 过期清理 |
| `players` | `roomId + openId` 唯一 | 防重复加入 |
| `players` | `roomId + playerId` 唯一 | 客户端引用 |
| `transactions` | `roomId + createdAt` | 流水列表 |
| `transactions` | `roomId + clientRequestId` 唯一 | 幂等 |
| `transactions` | `roomId + seq` 唯一 | 排序/对账 |
| `user_inbox` | `_id`（feedId）唯一 | 一人一条 feed，`doc(feedId).watch` |
| `asset_snapshots` | `roomId + playerId` 唯一 | 一人一份 |
| `settlements` | `roomId` 唯一 | 一局一份 |
| `room_events` | `roomId + createdAt` | 审计 |
| `rate_limits` | `expiresAt` | 清理 |

> 唯一索引要在云开发控制台或 `scripts/create-indexes.ts` 里显式创建；部署前作为检查项。

### 5.3 字段约定

- **金额**：整数 M，服务端校验 `Number.isInteger(amount) && amount > 0 && amount <= 1e9`；不存小数。
- **时间**：`Date.now()` 由云函数生成；客户端时间只用于展示。
- **openId**：只存在 `rooms.hostOpenId` / `players.openId` / `user_inbox.ownerOpenId`，不返回给其他玩家；客户端用 `playerId`。
- **status**：枚举服务端校验；不接受客户端自由字符串。
- **删除**：MVP 不做物理删除流水；房间过期后由 `timer` 清理/归档。

## 6. 核心链路

### 6.1 统一响应与错误码

请求：

```json
{
  "action": "playerPay",
  "payload": { "...": "..." },
  "clientRequestId": "uuid-v4"
}
```

成功：

```json
{ "ok": true, "data": { "...": "..." }, "serverTime": 1730000000000 }
```

失败：

```json
{ "ok": false, "error": { "code": "INSUFFICIENT_BALANCE", "message": "余额不足，请先收款/抵押/变卖", "details": { "balance": 50, "required": 200 } }, "serverTime": 1730000000000 }
```

错误码：

| code | 含义 | 客户端处理 |
|---|---|---|
| `INVALID_ARGUMENT` | 参数/金额/类别非法 | 提示并留在原页 |
| `ROOM_NOT_FOUND` | 房号不存在/已过期 | 回首页 |
| `ROOM_FULL` | 玩家已满 | 提示 |
| `ROOM_STATE` | 房间状态不允许该操作 | 刷新快照 |
| `NOT_MEMBER` | 不在房间 | 回首页 |
| `FORBIDDEN` | 非房主/非收款方等 | 隐藏入口 + 提示 |
| `INSUFFICIENT_BALANCE` | 余额不足 | 提示先收款/抵押/变卖 |
| `DUPLICATE_REQUEST` | 幂等键重复 | 当作成功，返回原交易 |
| `NOT_REFUNDABLE` | 该交易不可退 | 提示原因 |
| `ALREADY_TERMINAL` | 已退款/已冲正 | 刷新流水 |
| `NOT_SETTLING` | 不在结算中 | 刷新快照 |
| `ALREADY_SETTLED` | 已结算 | 只读 |
| `RATE_LIMITED` | 频率限制 | 提示稍后重试 |
| `INTERNAL` | 未预期错误 | 提示重试 + 上报 |

### 6.2 转账事务（核心）

```text
async transfer(ctx, input):
  return db.runTransaction(async tx => {
    room = tx.get(rooms, input.roomId)
    assert room.status in allowedStatuses(input.kind)

    actor = getPlayerByOpenId(tx, room._id, ctx.openid)
    assert actor exists

    // 解析付款方/收款方
    payer = resolve(tx, room, input.fromType, input.fromPlayerId)
    payee = resolve(tx, room, input.toType, input.toPlayerId)

    assert amount is integer and 0 < amount <= 1e9
    assert category in enum

    if payer.type == 'player':
      assert payer.status != 'bankrupt'
      assert payer.balance >= amount          // 不允许负余额
    // bank 不校验余额

    if payee.type == 'player':
      assert payee.status in ('active','bankrupt')  // 破产可被动收款

    seq = room.seq + 1
    if payer.type == 'player':
      tx.update(payer, { balance: payer.balance - amount })
    if payee.type == 'player':
      tx.update(payee, { balance: payee.balance + amount })

    txn = tx.add(transactions, {
      roomId, seq,
      fromType: payer.type, fromPlayerId: payer.playerId,
      toType: payee.type, toPlayerId: payee.playerId,
      amount,
      balanceAfterFrom: payer.type=='player' ? payer.balance - amount : null,
      balanceAfterTo:   payee.type=='player' ? payee.balance + amount : null,
      category, source, status: 'success',
      operatorId: actor.playerId,
      clientRequestId: ctx.clientRequestId,
      note, createdAt: now
    })

    tx.update(room, { seq, lastEventAt: now })

    // 只给收款人写 inbox；initial/reversal 不写
    if payee.type == 'player' and source in ('payment','salary','refund','bank_payment','chance','correction'):
      feed = tx.get(user_inbox, payee.feedId)
      events = [ ...(feed?.events || []), {
        transactionId: txn._id,
        type, fromLabel, amount, category,
        playSound: true, createdAt: now
      } ].slice(-50)
      tx.set(user_inbox, payee.feedId, {
        ownerOpenId: payee.openId,
        roomId, playerId: payee.playerId,
        events, updatedAt: now
      })

    return { transaction: txn, balances: ... }
  })
```

要点：

- **房间文档也在事务里写**：`seq`/`lastEventAt`。6 人房间并发低，值得用它换来“付款/结束/结算确认”之间的串行化；如果试玩发现冲突重试明显，再把 `lastEventAt` 拆出去，`seq` 改用 `room_counters`。
- **余额校验必须在事务内**：先读后写，不能先扣再补。
- **银行不校验余额**：银行是无限账户；但玩家向银行付款、玩家退款给银行，玩家一侧仍要校验。
- **破产玩家可以收款**：`status=bankrupt` 只限制主动付款/发起收款请求，不限制入账。
- **幂等**：`roomId + clientRequestId` 唯一索引；插入冲突时事务回滚，外层按 `clientRequestId` 查原交易返回。
- **入口先查幂等**：所有带 `clientRequestId` 的写动作，进事务前先查 `(roomId, clientRequestId)`；命中直接返回原结果。否则退款重试时原交易已 `refunded`，会在状态校验处误报失败。

### 6.3 开局发初始资金

优先单事务：

```text
startGame:
  tx:
    room = get(roomId); assert status == waiting
    players = query(roomId, isPlayer=true)
    assert players.length >= 2
    for p in players:
      update(p.balance += initialFunds)
      add(transactions, { source:'initial', amount: initialFunds, ... })
    update(room, { status:'playing', startedAt: now, seq: ... })
```

6 个玩家大约 6 次余额更新 + 6 条流水 + 1 次房间更新，通常在一个事务内可完成。初始资金交易**不写 `user_inbox`**，避免开局 6 连响；玩家进房看余额即可。若遇到事务操作数限制，走 fallback：

```text
startGame:
  room.fundingStatus = 'funding'
  对每个 isPlayer 且 fundedAt 为空的玩家:
    单事务：发钱 + 写流水 + fundedAt=now（幂等）
  全部完成后：room.status='playing', fundingStatus='done'
```

fallback 的好处是失败可重试，不会“半开房”；代价是 startGame 不是单事务，需要状态字段和重试逻辑。**M2 用 6 人房压测后再决定是否启用 fallback。**

状态动作也要幂等：`startGame` 若已 `playing` 直接返回快照；若 `funding` 继续发放未 `fundedAt` 的玩家；`endGame` 若已 `settling` 直接返回；`confirmSettlement` 若已 `settled` 返回 settlement；`resumeGame` 若已 `playing` 直接返回。避免网络重试导致二次发钱/二次结算。

### 6.4 退款与冲正

退款/冲正必须在**同一个事务**里完成“反向转账 + 原交易状态更新”，不能先调用 `transfer` 再单独改原交易。把 6.2 的转账逻辑抽成 `applyTransfer(tx, ctx, input)`，外层再包 `runTransaction`。

退款：

```text
refund(ctx, transactionId):
  return db.runTransaction(async tx => {
    original = tx.get(transactions, transactionId)
    assert original.status == 'success'
    assert original.source not in ('initial','refund','reversal')
    // 收款方发起：收款方是玩家时只能是该玩家；收款方是银行时只能是房主
    if original.toType == 'player':
      assert ctx.playerId == original.toPlayerId
    else:
      assert ctx.isHost
    assert amount == original.amount                // 全额

    result = applyTransfer(tx, ctx, {
      kind: 'refund',
      from: original.to, to: original.from,
      amount: original.amount,
      category: 'refund', source: 'refund',
      refundOf: original._id
    })

    tx.update(original, { status: 'refunded' })
    tx.add(room_events, { type:'refund', ... })
    return result
  })
```

冲正：

```text
reverse(ctx, transactionId, reason):
  assert ctx.isHost
  assert reason 非空
  return db.runTransaction(async tx => {
    original = tx.get(transactionId)
    assert original.status == 'success'
    assert original.source not in ('refund','reversal')

    result = applyTransfer(tx, ctx, {
      kind: 'reversal',
      from: original.to, to: original.from,
      amount: original.amount,
      category: 'correction', source: 'reversal',
      reversalOf: original._id
    })

    tx.update(original, { status: 'reversed' })
    tx.add(room_events, { type:'reversal', ... })
    return result
  })
```

`applyTransfer(tx, ...)` 负责：写反向流水、改双方余额、写 `room.seq/lastEventAt`、写收款人 inbox、返回结果；它不负责改原交易状态。原交易状态由 refund/reverse 在同一个事务里改。反向流水的 `category` 可记 `correction`，UI 用 `source=reversal` 显示“冲正”，不要只靠 category 区分退款/冲正/矫正。

关键边界：

- 原交易已 `refunded`/`reversed` → 拒绝。
- 退款/冲正不能造成负余额：反向转出方（原收款方）必须余额足够；不足则拒绝，提示先收款/抵押/变卖。
- 退款/冲正是终态；需要再修正走矫正（新的银行付款/收款）。
- 退款方是银行时不受余额限制；是玩家时校验余额。
- 并发双退：两个请求都读到 `success`，但 `room.seq` 写入会串行化事务；后提交者重试后看到 `refunded`，拒绝。


### 6.5 结算

```text
endGame(ctx, roomId):
  assert ctx.isHost
  tx:
    room = get(roomId); assert status == 'playing'
    update(room, { status:'settling', endedAt: now, settlingAt: now })
    add(room_events, { type:'end' })
```

```text
submitAssets(ctx, { roomId, playerId?, propertyValue, debt, note }):
  assert room.status == 'settling'
  target = ctx.isHost ? (playerId ?? ctx.playerId) : ctx.playerId
  assert target is a player
  upsert(asset_snapshots, roomId+target, { propertyValue, debt, note, updatedAt })

confirmSettlement(ctx, roomId):
  assert ctx.isHost
  tx:
    room = get(roomId); assert status == 'settling'
    players = query(roomId, isPlayer=true)
    assets = query(asset_snapshots, roomId)
    rankings = players
      .filter(p => p.isPlayer)
      .map(p => ({
        playerId, nickname, cash: p.balance,
        propertyValue: assets[p].propertyValue || 0,
        debt: assets[p].debt || 0,
        netWorth: p.balance + propertyValue - debt,
        bankrupt: p.status == 'bankrupt'
      }))
      .sort(netWorth desc)
    assign ranks（并列同名次）
    add(settlements, { roomId, rankings, createdAt: now })
    add(room_events, { type:'settle_confirm', ... })
    update(room, { status:'settled', settledAt: now })
```

`resumeGame`：

```text
resumeGame(ctx, roomId):
  assert ctx.isHost
  room.status == 'settling' -> 'playing'
  清 settlingAt/endedAt；保留 asset_snapshots（下次结算可覆盖）
  add(room_events, { type:'resume' })
```

```text
dissolveRoom(ctx, roomId):
  assert ctx.isHost
  tx:
    room = get(roomId)
    update(room, { status:'settled', settledAt: now, dissolvedAt: now, dissolvedBy: actor.playerId })
    add(room_events, { type:'dissolve' })
```

`settled` 后所有写操作拒绝；`dissolveRoom` 直接把房间置为只读（`status='settled'` + `dissolvedAt`），不生成排名。

`markBankrupt`：事务内改 `player.status`/`bankruptAt`，写 `room_events {type:'bankrupt', payload:{cancelled}}`；取消时 `status='active'`、清 `bankruptAt`。不能改银行-only 房主（`isPlayer=false`）。

### 6.6 读模型与实时

**快照**：

```text
getRoomSnapshot({ roomId }):
  assert member
  return {
    room: { code, status, hostIdentity, config, seq, ... },
    me: { playerId, isHost, isPlayer, isBanker, balance, feedId },
    players: [{ playerId, nickname, avatar, isPlayer, isBanker, balance, status }],
    transactions: last 30,
    serverTime
  }
```

银行-only 房主的 `me.feedId` 为 null（没有个人 inbox），靠轮询刷新；`isPlayer=false` 的玩家不写 inbox。玩家创建时生成 `feedId` + 空 `user_inbox` 文档；`inbox.events` 只保留最近 50 条。

**流水分页**：

```text
listTransactions({ roomId, beforeSeq?, limit=50 }):
  assert member
  query transactions where roomId and seq < beforeSeq order by seq desc limit
  return { items, nextCursor }
```

**实时**：

- 收款人：`db.collection('user_inbox').doc(feedId).watch(...)`；对比 `events` 数组里的 `transactionId`，只处理新事件，播放音效/横幅/震动，并触发一次快照刷新。
- 重连/回前台：`listInbox({ roomId, after })` 拉最近未播放事件；只对最近 2 分钟的事件补响，避免旧事件重放。
- 其他玩家：页面可见时每 3 秒 `getRoomSnapshot`；`onShow` 立即拉一次；`onPullDownRefresh` 手动刷新。
- `watch` 报错/断线：降级为 3 秒轮询；重连后拉快照，不依赖增量。
- 所有集合除 `user_inbox` 外，客户端不直读；`user_inbox` 安全规则 `read: doc.ownerOpenId == auth.openid`，`write: false`。

**为什么不让客户端直接 watch `rooms`/`transactions`？**

- 安全规则不能跨集合判断“我是不是这个房间的成员”；
- 直接读会把 `openId`/其他玩家信息暴露给客户端；
- 6 人房间用 inbox + 轮询足够，且实现更稳。

### 6.7 音效

- 预加载 `innerAudioContext`，资源放小程序包内（几十 KB）。
- 收款人收到 `user_inbox` 事件后：
  - 校验 `event.playerId === me.playerId`；
  - 按 `transactionId` 去重，避免重连/重放重复响；
  - 进入队列，串行播放，避免重叠；
  - `wx.vibrateShort` + 横幅。
- 退款到账：原付款人是收款人，正常响；退款发起人只看到成功页。
- 工资到账：收款玩家响。
- 银行收款：不响。
- 音效开关：`room.config.soundEnabled` 且收款人本地开关都开才播；流水仍记录。
- 写 inbox 的 source：`payment / salary / refund / bank_payment / chance / correction`（且收款方是玩家）；`initial`、`reversal` 不写 inbox；冲正默认不响，受影响玩家以流水为准。
- 小程序后台/锁屏不保证播放；回到前台拉快照，流水为准。
- `wx.setInnerAudioOption({ obeyMuteSwitch: false })` 尽量在静音下可听，但不保证所有机型。

### 6.8 房号、二维码、限流

- 房号：6 位数字；`room_codes._id = code` 天然唯一；创建时**同事务**插入 `room_codes` + `rooms`，冲突重试 5 次。
- 二维码：`cloud.openapi.wxacode.getUnlimited({ scene:'r='+code, page:'pages/join/index' })`；生成后存云存储，`getRoomQr` 返回 fileID；过期/删除后重新生成。
- 开发环境小程序未发布时，`getUnlimited` 可能不可用；用普通二维码/房号兜底，不阻塞开发。
- 加入限流：`rate_limits` 按 `openid:minute` 计数，超过 10 次/分钟拒绝；`timer` 清理过期计数。
- 房号错误/满员/已开始/已过期分别返回明确错误码。
- `createRoom`：`memberCount = hostIdentity === 'dual' ? 1 : 0`；双身份房主本身占 1 个玩家名额，银行-only 不占。
- `joinRoom` 必须在房间文档事务里做：读 `room.memberCount`，`< maxPlayers` 才创建玩家并 `memberCount+1`；不要“先 count 再 add”，否则并发加入会超员。

### 6.9 权限与安全

- `openid` 一律从 `cloud.getWXContext().OPENID` 取；不信任客户端传的 openid。
- 所有写操作走 `api`；数据库安全规则：除 `user_inbox` 外，客户端不可读、不可写。
- 服务端逐动作校验：成员、房主、房间状态、操作者角色、目标玩家、金额、类别、备注长度。
- 房主权限不能只靠前端隐藏按钮；`bankPay`/`paySalary`/`bankCollect`/`reverse`/`markBankrupt`/`confirmSettlement`/`resumeGame`/`dissolveRoom` 都要服务端校验。
- 退款只能原收款方；冲正只能房主；银行-only 房主不能个人收付；双身份付款必须显式 `fromType`。
- `openId` 不出现在任何客户端响应；日志用 `playerId`，不打印 openId。
- 房号加入限流；金额上限；备注 50 字；类别枚举；防注入（参数化查询）。
- 数据保留：房间 24 小时无活动过期；`timer` 清理房间、玩家、流水、inbox、asset、settlement；试玩分析只留聚合数据。

### 6.10 过期清理

`timer` 每小时：

- `rooms.expiresAt < now` 且非 `settled`：标记过期/删除；
- 删除对应 `players`、`transactions`、`user_inbox`、`asset_snapshots`、`room_events`；
- 清理 `room_codes`、`rate_limits`；
- 保留 `analytics_events` 的聚合数据（不含 openId）。

## 8. 客户端设计

### 8.1 页面与状态

| 页面 | 主要状态 | 数据来源 |
|---|---|---|
| 首页 | 最近房间、登录态 | `getRoomSnapshot`（最近房间可选） |
| 加入房间 | 房号/二维码、昵称/头像 | `joinRoom` |
| 创建房间 | 表单、提交中 | `createRoom` |
| 大厅 | 玩家列表、房号/二维码、开始 | `getRoomSnapshot` |
| 账房主页 | 我的余额、玩家余额、最近流水 | `getRoomSnapshot` |
| 银行控制台 | 玩家余额、发工资、付款/收款、累计发行 | `getRoomSnapshot` + 动作 |
| 付款页 | 收款人、金额、类别、来源 | store + `playerPay` |
| 流水页 | 分页、筛选、详情、退款 | `listTransactions` |
| 结算页 | 资产/负债、排名、确认 | `getRoomSnapshot` + `submitAssets` / `confirmSettlement` |
| 设置/帮助 | 音效、规则、解散 | 本地 + 动作 |

### 8.2 状态管理

- 不引重库；一个简单的 `roomStore`（observable）+ 页面 `setData`。
- `roomStore` 持有：`room`、`me`、`players`、`transactions`、`serverTime`、`loading`。
- 所有余额以服务端返回为准；**不做乐观扣款**，避免“看起来成功但没到账”。
- 付款按钮：提交中禁用；成功后跳成功页；失败按错误码提示。
- `clientRequestId` 每次“新的付款意图”生成一个 UUID；重试复用同一个；成功/失败后清空。

### 8.3 付款交互

1. 选收款人（最近玩家/玩家列表/银行）。
2. 输金额（整数），选类别，备注可选。
3. 双身份显示“我的钱/银行”来源；默认“我的钱”。
4. 展示付款前后余额；余额不足禁用确认。
5. 确认 → `playerPay` / `bankPay` / `bankCollect` / `paySalary`。
6. 成功页；收款人 inbox 触发音效。
7. 失败：余额不足 → 提示先收款/抵押/变卖；重复请求 → 当成功；状态错误 → 刷新快照。

### 8.4 实时与音效

- `realtime.ts` 启动时：`getRoomSnapshot` → 拿 `feedId` → `watch(user_inbox)`。
- inbox 事件 → `audio.play(event)` + `refreshSnapshot()`（debounce 300ms）。
- 页面 `onShow`：立即刷新 + 重新 watch；`onHide`：停止轮询。
- 轮询：3 秒一次；`watch` 正常时也保留低频轮询（可选 10 秒）做兜底。
- 音效去重：`Set<transactionId>`，保留最近 50 个。
- 多设备：同一 openid 可能两条 watch；MVP 允许重复音效，P1 加设备心跳。

### 8.5 错误与空状态

- 房间不存在/已过期/已满/已开始：明确文案 + 回首页。
- 余额不足：显示当前余额、应付金额、差额，给“去收款/抵押”入口。
- 已结算：页面只读，禁用所有付款/退款/冲正按钮。
- 网络异常：Toast“网络异常，请重试”，不排队、不离线付款。
- 空流水/空玩家：占位文案。

## 9. 测试策略

### 9.1 单元测试（ledger-core）

- 转账：玩家→玩家、玩家→银行、银行→玩家；余额不足；银行无限；破产付款被拒。
- 退款：只有收款方能退；全额；开局资金/退款/冲正不可退；余额不足拒绝；终态。
- 冲正：只有房主；原因必填；已退款/已冲正不能再冲；余额不足拒绝。
- 结算：净资产公式；银行-only 排除；破产标记；并列名次；未填资产按 0。
- 权限：非房主不能 bankPay/paySalary/bankCollect/reverse/confirm；非收款方不能退款。
- 幂等：同一 clientRequestId 返回原交易。

### 9.2 集成测试（FakeRepo + 云环境）

- `FakeRepo` 实现房间/玩家/交易/资产的内存存储，跑完整用例。
- 云环境脚本：建房 → 加入 → 开局 → 100 笔付款 → 对账；检查 `sum(transactions) == balance`。
- 并发：同一付款人 10 笔并发（余额足够），全部成功且余额正确；余额只够 5 笔时，5 成功 5 拒绝。
- 重复：同一 clientRequestId 连发 3 次，只成交一次。
- 开局：模拟 6 人；注入失败，重试后不重复发钱、不半开房。
- 结算竞态：settling 确认与付款并发，确认后付款必须失败。

### 9.3 手工试玩

按产品设计附录 A.3 跑：

1. 6 人局，银行-only/双身份各一局。
2. 初始资金、工资、玩家付款、玩家付银行、银行付款。
3. 余额不足、退款、冲正、破产标记/取消。
4. 结算返回、确认、只读。
5. 断线、离线收款、房主换设备。
6. 音效（收款人/工资/退款/银行收款静音）。
7. 权限（非房主、付款方不能退款）。
8. 异常（重复点击、房号错误/满员/过期）。

### 9.4 测试数据

- `scripts/seed-dev.ts`：在 dev 环境创建测试房间/玩家；只在 dev 云函数启用。
- `scripts/consistency-100.ts`：调用 `api` 做 100 笔付款并核对；输出差异。
- 测试 openid：dev 环境允许 `__devOpenId` 注入，生产环境禁用（环境变量守卫）。

## 10. 部署与运维

### 10.1 环境

- 云开发环境：`dev` / `prod` 两个；`wx.cloud.init({ env })` 按小程序环境切换。
- 云函数运行时：Node 16/18（以云开发控制台可用版本为准）。
- 数据库索引：部署前按 5.2 创建；写一个 `scripts/create-indexes.ts` 或控制台清单。
- 云存储：二维码图片、音效（音效也可放包内）。

### 10.2 构建与发布

- 小程序：`tsc` + TDesign npm 构建；`miniprogram-ci` 上传体验版。
- 云函数：esbuild 打包 `api`/`timer`；DevTools 或 CloudBase CLI 部署。
- CI：lint + typecheck + Jest；部署先手动，试玩稳定后再自动化。
- 版本：`api` 返回 `serverTime`/`version`；数据库变更写迁移脚本。

### 10.3 日志与监控

- 云函数日志：JSON 一行，包含 `action`、`roomId`、`playerId`、`code`、`duration`；不打印 openId。
- 错误：按错误码聚合；`INTERNAL` 单独告警。
- 试玩指标：`analytics_events` + 数据库查询；不采集手机号/位置。
- 预算：云开发控制台设置预算提醒；试玩期每天看用量。

### 10.4 数据保留

- 房间 24 小时无活动过期；`timer` 清理房间、玩家、流水、inbox、资产、结算。
- 试玩分析保留聚合数据，不保留 openId。
- 上线前准备隐私政策、数据删除说明。

### 10.5 成本估算（6 人试玩）

> 具体价格以云开发控制台账单页为准；下面是量级估算，不是报价。

假设：6 人、单局 3 小时、每局约 100 笔付款；5 个非收款玩家每 3 秒轮询（收款人走 inbox）；每月 4 局（每周 1 局）。

| 项目 | 估算 |
|---|---|
| 云函数调用 | 约 7–8 万次/月（轮询约 7.2 万 + 付款 400） |
| 数据库读 | 约 40–50 万次/月（每次快照读房间 + 6 个玩家） |
| 数据库写 | 几千次/月 |
| 实时连接 | 6 个 |
| 存储 | < 100 MB |
| CDN/流量 | < 1 GB |

| 费用项 | 估算 |
|---|---|
| 小程序注册 | ¥0（个人主体） |
| 云开发 | 免费额度内 ¥0；最低付费套餐约 ¥20–70/月 |
| 认证/发布 | 体验版 ¥0；发布/认证按平台当期标准（几百元/年） |
| 域名/服务器/HTTPS | ¥0（云开发自带） |
| 微信支付/商户号 | ¥0（不接真钱） |
| 短信/推送 | ¥0（MVP 不需要；P1 订阅消息免费） |
| **合计** | **¥0–70/月；约 ¥0–840/年；含可选认证约 ¥0–1,100/年** |

结论：6 个人、每周 1 局，现金成本大概率是 **0 元/月**（免费额度内）；即使买最低套餐，也就 **20–70 元/月**，人均每局不到 3 元。开发成本另算：自己写是 5–8 周时间，外包按人天询价。

省钱的几个做法：

- 只在前台轮询，3–5 秒；页面隐藏停止；收款人走 inbox。
- `getRoomSnapshot` 用 `sinceSeq` 只拉增量，别每次返回 30 条流水。
- 一个云环境跑试玩；过期房间/数据用 `timer` 清。
- 控制台设置预算提醒（如 20/50 元）；试玩期每天看用量。
- 只给朋友玩用体验版，不发布/不认证；体验成员名额通常足够 6 人（以小程序后台为准）；`wxacode.getUnlimited` 不可用时用房号兜底。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 云数据库事务冲突/操作数限制 | 付款失败、开局半完成 | 事务尽量短；6 人压测；开局 fallback 逐人发放；冲突重试 |
| `watch` 权限/连接数限制 | 收款人收不到实时提示 | M0 做最小 spike；inbox + 轮询兜底；重连拉快照 |
| 音效在后台/锁屏不播 | 收款人漏提示 | 以流水为准；回前台拉快照；P1 订阅消息/全房播报 |
| `wxacode.getUnlimited` 需已发布小程序 | 开发期无法生成码 | 房号/普通二维码兜底；发布后启用 |
| 小程序类目/商标审核 | 上线被拒 | 用“桌游账房/工具”定位；Monopay 商标检索；备选名 |
| 房主掉线 | 银行付款暂停 | 同微信另一设备登录恢复；P1 房主转让 |
| 无负余额导致退款/冲正失败 | 玩家觉得“退不回” | 提示先收款/抵押/变卖；MVP 只记抵押金额；P1 资产登记 |
| 房间文档热写 | 高并发冲突 | 6 人可接受；监控冲突率；必要时拆 `lastEventAt`/`seq` |
| 多设备同账号 | 音效重复 | MVP 接受；P1 设备心跳/最后活跃设备 |
| 冷启动 | 首笔付款慢 | 单 `api` 函数、依赖最小；必要时预留实例 |
| 数据清理遗漏 | 隐私/成本 | `timer` 定时清理；部署检查清单 |

## 13. P1 扩展点

架构不锁死，以下功能可以在不改账本核心的前提下加：

- **收款请求**：新增 `payment_requests` 集合 + `create/respond` 动作；账本仍走 `transfer`。
- **部分退款**：交易加 `refundedAmount`/`refundable`；退款金额 ≤ 剩余；UI 支持输入金额。
- **地产/租金**：新增 `properties`/`ownership`；付款页根据登记建议租金；结算资产自动汇总；账本不变。
- **房主转让**：更新 `rooms.hostOpenId` + 审计事件；银行权限随房主转移；账本不变。
- **批量收付**：循环调用 `transfer`，每笔一个 `clientRequestId`；返回成功/失败明细。
- **订阅消息/全房播报**：在 inbox 之外加 `wx.requestSubscribeMessage` 或房间事件推送。
- **单机/离线**：本地账本适配器；MVP 不做。

## 14. 待确认的技术决策

以下是我建议的默认值；如果没异议，按这个开工：

1. **单 `api` 云函数 vs 多函数**：建议先单函数 + action 路由，后续按热点拆。
2. **实时模型**：建议 `user_inbox` 只推收款人 + 其他玩家 3 秒轮询；不直接 watch 房间/流水。
3. **UI 库**：建议 TDesign Mini Program；如果团队更熟 Vant，可换，不影响架构。
4. **`seq`/房间热写**：建议先保留房间文档事务写；试玩冲突明显再拆 `lastEventAt`/`room_counters`。
5. **云函数语言**：建议 TypeScript + esbuild 打包；如果只想快，JS 也能跑，但共享类型会弱。
6. **试玩分析**：建议 `analytics_events` + 云函数日志；不接第三方统计，避免隐私和审核问题。

## 15. 开工顺序（第一周）

1. 建小程序项目 + 云环境 + TDesign + TS。
2. 建 `api` 云函数 + `ledger-core` + 错误码 + `getRoomSnapshot` 空实现。
3. 建集合/索引：`rooms`、`players`、`transactions`、`user_inbox`、`room_codes`。
4. 做 `createRoom` / `joinRoom` / `startGame`，打通“建房→加入→开局发钱”。
5. 做 `playerPay`，打通“付款→扣款→写流水→收款人 inbox”。
6. 用 2 个测试账号跑通一局最小闭环，再进入退款/结算。

> 第一周的目标不是“功能多”，而是把 **openid → 房间 → 事务 → 流水 → 实时** 这条主链路跑通；后面的功能都是这条链路上的分支。
