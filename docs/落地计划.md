## 0. 一页纸

**目标**：让 2–6 个人用手机浏览器完成一局桌游的完整资金流转——开房、加入、发初始资金、付款、银行操作、退款/冲正、结算对账——并且能通过 Docker Compose 部署到现有服务器。

**交付节奏**：

```text
M0 工程与部署闭环
  ↓
M1 房间生命周期
  ↓
M2 账本核心与付款        ← 最重、风险最高
  ↓
M3 纠错、流水与结算
  ↓
M4 体验与实时打磨
  ↓
M5 验收与上线
```

**关键路径**：M0 → M1 → M2 → M3 → M5。  
M4 的视觉、音效、主题可以穿插在 M2/M3 中做，但最终验收必须在 M3 之后。

**估算**：26–36 人日；1 人全职约 5–7 周，业余约 9–13 周。  
产品文档里的 4–6 周是顺利情况；本计划把测试、部署、试玩修复算进去。

**阶段产物**：

| 阶段 | 产物 |
|---|---|
| M3 结束 | Alpha：能完整玩一局，内部试玩 |
| M4 结束 | Beta：手机体验、音效、主题、重连达标 |
| M5 结束 | v1.0：生产部署、备份、验收通过 |

## 1. 范围与边界

### 1.1 本计划纳入

- 房间：创建、加入、开始、结束、解散、24 小时过期、断线重连。
- 房主身份：银行-only / 双身份；创建后不可改；双身份切换操作台。
- 钱：初始资金、工资、玩家付款、银行付款/收款、余额校验、不允许负余额。
- 纠错：退款、冲正、矫正、破产标记/取消。
- 流水：全员可见、筛选、详情、状态关联。
- 结算：资产估值、负债、净资产排名、确认/返回、只读。
- 实时：WebSocket 推送、快照补偿、断线重连。
- 体验：默认主题 A、B–F 切换、移动端布局、动效、音效/横幅/震动、错误态。
- 部署：Docker Compose、Caddy HTTPS、SQLite 持久化、GHCR 镜像、备份/恢复。

### 1.2 本计划不纳入

- 收款请求、部分退款、批量收付、借款/欠条、地产登记、自动租金。
- 账号体系、微信登录、房主转让、多设备 session 管理。
- 聊天、排行榜、战报分享、再来一局、旁观/投屏。
- 真钱、充值、提现、兑换。
- 单机/离线模式、PWA 离线缓存。
- 多副本部署、Redis、消息队列、Kubernetes。
- 后台管理、桌游吧 B 端、多语言。

### 1.3 范围冻结规则

1. 任何 P1 功能不得插入 M0–M5；只能记入 `P1 backlog`。
2. 任何规则变更先改产品设计，再改 `ledger-core` 测试，再改实现。
3. 任何新增页面先判断是否属于 MVP 验收标准；不属于就不做。
4. 不接受“先做出来再补测试”的账本核心代码。

## 2. 交付原则

1. **Walking skeleton 优先**：M0 先把“浏览器 → HTTPS → Fastify → SQLite → 镜像 → 服务器”跑通，再写业务。
2. **纵向切片**：每个里程碑都包含 DB、API、UI、实时、测试、部署，不做“后端全写完再写前端”。
3. **账本核心单一实现**：转账、退款、冲正、结算规则只写在 `packages/ledger-core`，前端不复制规则，后端路由不写第二套。
4. **Contract first**：先定 Zod schema、API 响应、错误码、WS 事件，再写页面和路由。
5. **每个里程碑可部署**：M0 之后，每次合并到 main 都能产出镜像；不等到最后才上服务器。
6. **正确性优先于视觉，但视觉是验收项**：钱算错是 P0；页面不好看也不能发版。
7. **单实例约束**：SQLite + 进程内 WS，只允许 1 个 app 副本；不执行 `--scale app=2`。
8. **一次只开一个里程碑**：上一个 Gate 不通过，不进入下一个。

| **合计** | | | **26–36** | |

### 3.1 依赖关系

```text
M0 ──► M1 ──► M2 ──► M3 ──► M5
                    │
                    └──► M4（可提前穿插，Gate 在 M3 后）
```

- M2 是最大风险：账本核心、幂等、并发、WS 都在这里。
- M3 的结算依赖 M2 的交易和余额模型。
- M4 不改变规则，只改体验；不允许在 M4 加 P1 功能。
- M5 只修 P0/P1 缺陷，不扩范围。

### 3.2 参考排期（1 人全职，非承诺）

| 周 | 内容 | 备注 |
|---|---|---|
| W1 | M0 + M1 起步 | 先把部署闭环打通，再开房 |
| W2–W3 | M2 账本核心与付款 | 最重；不要压缩测试 |
| W4 | M3a 纠错与流水 | 退款/冲正/破产 |
| W5 | M3b 结算 + M4 起步 | 结算 Gate 后再做体验 |
| W6 | M4 + M5 起步 | 主题/音效/重连/验收 |
| W7 | 缓冲 + 试玩修复 | 只修 P0/P1，不加功能 |

## 5. M1：房间生命周期

**目标**：房主能开房，2–6 名玩家能通过 URL/二维码/房号加入，刷新能重连，房主能在大厅看到人。  
**不包含**：开始游戏、发钱、付款。

### 5.1 任务

| ID | 任务 | 产出 |
|---|---|---|
| ROOM-01 | 数据模型 | `rooms`、`players` 表；`code` 唯一；`host_identity`、`token_hash`、`config_json`、`seq` |

### 5.2 Gate G1

- [ ] 房主只能创建“银行-only”或“双身份”，不能创建纯玩家；参数校验正确。
- [ ] 创建页默认双身份/初始资金 2000/最大 6 人/工资 200/大额阈值 1000/音效开；初始资金 >0、人数 2–6。
- [ ] 6 名玩家可加入；第 7 名被拒绝；银行-only 房主不占名额。
- [ ] 同一 `playerToken` 重复加入按重连处理，不重复创建玩家。
- [ ] 开局后新玩家不能加入；玩家不能主动退出；只能由房主解散。
- [ ] 刷新页面、关闭再打开，仍能回到原房间。
- [ ] 非房主看不到银行台入口；直接调接口返回 `FORBIDDEN`。
- [ ] 手机扫码/打开 `/r/CODE` 或输入 6 位房号都能进入加入页。
- [ ] 大厅实时显示新加入玩家；WS 断开后能重连。
- [ ] 房主解散后房间只读；24 小时无活动清理能跑。
- [ ] 390px 宽度无横向滚动；关键按钮 ≥44px。

## 6. M2：账本核心与付款

**目标**：一局能开始，初始资金只发一次；玩家能付款；房主能用银行台发工资、付款、收款；余额、流水、实时全部正确。  
**这是全项目最重、最不能返工的阶段。**

### 6.1 任务拆分

#### M2a：账本核心（先做，不碰 UI）

| ID | 任务 | 产出 |
|---|---|---|
| LEDGER-01 | 领域模型 | `packages/ledger-core`：Account、Transaction、Command、错误类型；纯 TS，无 DB/HTTP |
| LEDGER-02 | 核心命令 | `startGame`、`playerPay`、`bankPay`、`bankCollect`、`salary`；返回新余额、transaction、events |
| LEDGER-03 | 事务仓储 | `transactions` 表；`BEGIN IMMEDIATE`；`room.seq` 递增；`balance_after_from/to`；索引 |
| LEDGER-04 | 幂等 | `UNIQUE(room_id, client_request_id)`；重复请求返回原交易，不重复扣款 |
| LEDGER-05 | 开局 | `POST /actions/start`；至少 2 名玩家；初始资金仅一次；写 `initial` 流水；状态 `playing` |
| LEDGER-06 | 玩家付款 | `POST /actions/pay`；玩家→玩家/银行；余额校验；类别/备注；大额阈值只做前端确认 |
| LEDGER-07 | 银行操作 | `POST /actions/bank-pay`、`bank-collect`；仅 host；银行无限；工资默认 200、不二次确认 |
| LEDGER-08 | 查询 | `GET /transactions` 分页；snapshot 带最近流水；`me` 带余额/身份 |
| LEDGER-09 | WS 事件 | 交易后广播 `transaction`/`player`/`room`；客户端按 `seq` 补快照 |

#### M2b：账本 UI 与银行台

| ID | 任务 | 产出 |
|---|---|---|
| UI-01 | 我的账本 | 余额卡、快捷付款、玩家余额、最近流水；银行-only 显示银行入口 |
| UI-02 | 付款页 | 收款人、金额键盘、快捷金额、类别 chips、备注、双身份“我的钱/银行”、前后余额、确认 |
| UI-03 | 银行台 | 玩家余额、累计发行/回收、工资、银行付款、银行收款、机会卡/矫正入口占位 |
| UI-04 | 状态与错误 | 余额不足、房间状态、网络失败、重复提交、成功页；文案按产品设计 |
| UI-05 | 双身份 | 操作台切换（我的账本/银行台）；切换不产生资金变动；来源标识清楚 |

### 6.2 关键规则（必须按此实现）

- 金额整数 M，`>0`，上限 `1e9`；不支持小数。
- 玩家转出：`balance >= amount`；不足拒绝，不允许负余额。
- 银行无限，不参与排名；银行-only 无个人余额。
- 每笔交易记录双方交易后余额；房间 `seq` 单调递增。
- 双身份付款必须显式 `fromType: player | bank`；银行台交易一律 `bank`。
- 工资：单人，默认 200，可改，不二次确认；类别固定“工资”。
- 快捷金额：10 / 50 / 100 / 200 / 500 / 上次金额；备注 ≤50 字。
- 大额二次确认：普通付款超过阈值（默认 1000）时确认；开局资金、工资、退款豁免。
- 初始资金：开局批量一次；重连/切操作台/结算不重复。
- 付款人必须在线：客户端离线时禁用付款；服务端不提供离线排队。收款人可以离线，到账后重连查看。
- 类别枚举覆盖：租金、购买、税费、罚款、机会/命运、抵押/变卖、借款、还款、交易、工资、退款、矫正、其他。
- 破产的双身份房主保留银行操作权，但不能用银行给自己（玩家身份）付款。
- 幂等：同一 `clientRequestId` 只成交一次；完全相同请求返回原交易；同键不同参数返回 `DUPLICATE_REQUEST`，不能静默复用。
- WS 只负责通知；断线后以 snapshot + `seq` 为准。

### 6.3 Gate G2

#### G2a：账本正确性

- [ ] 2–6 人开局，每人只收到一次初始资金；银行-only 没有余额、不能发起个人付款。
- [ ] 玩家→玩家、玩家→银行、银行→玩家、工资都能成功。
- [ ] 余额不足拒绝；收款不受余额限制；银行付款不受限制。
- [ ] 双身份“我的钱/银行”来源正确；银行→房主玩家显示清楚。
- [ ] 连续 100 笔付款后，余额与流水完全一致。
- [ ] 重复点击/网络重试不会重复扣款。
- [ ] 6 人并发付款不出现负余额；同一付款人并发只成交余额允许的部分。
- [ ] 付款人离线时不能发起付款；收款人离线仍可到账，重连可查。
- [ ] 破产的双身份房主不能用银行给自己（玩家身份）付款。
- [ ] 每笔余额变化都能追溯到一笔流水；`balance_after` 正确。
- [ ] 银行台累计发行/回收 = 银行付款总额 − 银行收款总额。

#### G2b：操作体验

- [ ] 付款中位时长 ≤8 秒（正常网络、手机尺寸）。
- [ ] 收款人 1 秒内看到到账；其他玩家静默更新。
- [ ] 付款成功页、余额不足提示、网络错误提示都明确。
- [ ] 普通付款超过 1000 有二次确认；工资/退款/开局资金不触发。
- [ ] 快捷金额和“上次金额”可用；备注超过 50 字被限制。
- [ ] 银行台只有房主能打开；非房主接口调用被拒绝。

## 7. M3：纠错、流水与结算

**目标**：一局能从 `playing` 走到 `settled`，中间能退款、冲正、矫正、标记破产，最后按规则排名并只读。

### 7.1 M3a：纠错与流水

| ID | 任务 | 产出 |
|---|---|---|
| CORR-01 | 退款 | `POST /actions/refund`；仅原收款方；全额；原路退回；终态；开局资金/退款/冲正不可退 |
| CORR-02 | 冲正 | `POST /actions/reverse`；仅房主；必填原因；原流水保留；反向流水；终态 |
| CORR-03 | 矫正 | 银行付款/收款类别“矫正”；必填原因；不修改历史流水 |
| CORR-04 | 破产 | `bankrupt` 标记/取消；不能主动付款；可被动收款；取消后恢复主动付款；排名标记；写房间事件 |
| TX-01 | 流水页 | 倒序、分页、筛选（全部/我付出/我收到/银行）、详情、状态、关联退款/冲正 |
| TX-02 | 退款入口 | 收款方在流水详情发起；付款方看不到退款按钮；银行作为收款方同理 |

**关键约束**：

- 退款/冲正不能造成任何玩家负余额；余额不足则拒绝，提示先补足。
- 同一笔原交易只能被退款或冲正一次；退款/冲正交易本身不能再退/冲。
- 退款/冲正与原交易状态更新必须在同一个事务。
- 不允许删除或静默修改流水。

### 7.2 M3b：结算

| ID | 任务 | 产出 |
|---|---|---|
| SETTLE-01 | 结束 | `POST /actions/end`：`playing → settling` |
| SETTLE-02 | 资产/负债 | `POST /actions/assets`：玩家填自己的；房主可代填/修正并留原因 |
| SETTLE-03 | 返回对局 | `POST /actions/resume`：确认前可回 `playing` |
| SETTLE-04 | 确认结算 | `POST /actions/confirm`：净资产 = 现金 + 资产 − 负债；排名；快照；`settled` |

| SETTLE-06 | 只读 | `settled` 后拒绝付款/退款/冲正/改资产；页面只读 |

## 10. 接口与模块边界

### 10.1 包职责

| 位置 | 职责 | 禁止 |
|---|---|---|
| `packages/shared` | Zod schema、API 类型、错误码、WS 事件类型 | 依赖 Vue/Fastify/DB |
| `packages/ledger-core` | 纯账本规则、命令、结果、事件 | 读写 DB、HTTP、时间/随机数副作用 |
| `apps/server/src/usecases` | 鉴权、权限、事务编排、调用 ledger-core | 复制账本规则 |
| `apps/server/src/repo` | SQLite/Drizzle、事务、查询 | 业务规则 |
| `apps/server/src/routes` | HTTP 解析/校验/响应 | 直接改余额 |
| `apps/web/src/services` | API/WS/audio | 复制账本规则 |
| `apps/web/src/stores` | session/room/ledger 状态 | 直接写余额 |
| `deploy/` | compose/Caddy | 业务代码 |

### 10.2 接口冻结点

在 M2 开始前冻结：

- `ApiResponse<T>` envelope 和错误码。
- 房间/玩家/交易/结算的 Zod schema。
- WS 事件名：`transaction`、`player`、`room`、`settlement`、`kick`。
- `seq` 语义：房间状态版本，交易/状态事件递增；客户端记录 `lastSeq`。
- token：随机 128-bit，服务端只存 hash；host/player 分开。
- 金额：整数 M；`balance_after_from` / `balance_after_to` 必填。

### 10.3 API 分组

| 里程碑 | 接口 |
|---|---|
| M1 | `POST /api/rooms`、`POST /api/rooms/:code/join`、`GET /api/rooms/:code/snapshot` |
| M2 | `POST /actions/start`、`POST /actions/pay`、`POST /actions/bank-pay`、`POST /actions/bank-collect`、`GET /transactions` |
| M3 | `POST /actions/refund`、`POST /actions/reverse`、`POST /actions/bankrupt`、`POST /actions/end`、`POST /actions/resume`、`POST /actions/assets`、`POST /actions/confirm`、`POST /actions/dissolve` |

> 所有写操作都带 `clientRequestId`；所有响应带 `serverTime`；所有错误有稳定 `code`。

## 11. 数据不变量与测试矩阵

### 11.1 必须永远成立

1. 任何余额变化都对应一笔 `transactions`。
2. 任何玩家余额 `>= 0`。
3. `sum(players.balance) = 初始资金总额 + 银行付款 − 银行收款`（退款/冲正按净额抵消）。
4. 房间内 `seq` 单调递增；`transactions.seq` 唯一。
5. 每笔交易 `balance_after_from/to` 与流水重放结果一致。
6. 同一 `(room_id, client_request_id)` 只产生一笔交易。
7. 退款/冲正/结算终态不可逆；`settled` 后无写操作。
8. 初始资金只发一次；重连/切操作台不产生资金变动。
9. 银行-only 无个人余额、不参与排名、不占玩家名额。
10. 结算快照写入后不可变。

### 11.2 测试层级

| 层级 | 工具 | 覆盖 | Gate |
|---|---|---|---|
| 单元 | Vitest | `ledger-core` 每个命令、边界、终态、幂等 | G2/G3 |
| API | Fastify inject | 房间生命周期、权限、付款、退款、结算、错误码 | G2/G3 |
| WS | ws 客户端 | 鉴权、广播、seq、重连 | G2 |
| 一致性 | 脚本 | 100/1000 笔随机/顺序交易重放 | G3/G5 |
| 并发 | 脚本 | 6 人并发、同一付款人并发、结算竞态 | G2/G5 |
| E2E | Playwright | 开房→加入→付款→退款→结算；双浏览器 | G4/G5 |
| 手动 | 真机 | iOS Safari、Android Chrome、微信内打开 | G4/G5 |
| 恢复 | 脚本 | 备份→删库→恢复→快照一致 | G5 |

### 11.3 覆盖目标

- `ledger-core` 分支覆盖 ≥90%，所有错误分支必须有测试。
- 账本相关 API 的正常/错误路径都要有集成测试。
- 不追求全项目覆盖数字；关键路径必须有测试。

## 12. CI/CD、环境与发布

### 12.1 CI 门禁

每次 push / PR：

```text
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm build
docker build（仅 main/tag）
```

任何一步失败不得合并。

### 12.2 镜像发布

- `main` → `sha-<short>`、`main`、`latest`。
- `v*` tag → `x.y.z`、`x.y`、`sha-<short>`。
- 生产固定 `MONOPAY_TAG=v1.0.0`，不用 `latest`。
- GHCR 包默认 Private；上线前改为 Public，或服务器登录。

### 12.3 环境

| 环境 | 用途 | 数据 |
|---|---|---|
| local | 开发、单测、E2E | `./data/dev.db` |
| production | 真实试玩 | `./data/monopay.db` |
| staging（可选） | 上线前演练 | 独立目录/域名 |

MVP 不强制 staging；如果服务器资源允许，建议用同 compose 起一个 `monopay-staging`，端口/域名不同。

### 12.4 迁移与回滚

- 迁移只前进，不写破坏性变更；上线前备份。
- 启动时自动迁移；失败则不健康，Caddy 不接流量。
- 回滚镜像时，若 schema 已变，优先恢复备份；不要假设旧镜像能读新表。
- 每次发布记录：tag、镜像 digest、迁移版本、备份文件。

### 12.5 单实例

- 只运行 1 个 app 副本；SQLite + 进程内 WS 不支持多副本。
- 需要扩容时，先换 Postgres + Redis/pub-sub，另立计划。

## 13. 风险清单

| 风险 | 影响 | 应对 | 触发信号 |
|---|---|---|---|
| 当前 origin 不是 GitHub | 无法用 GitHub Actions/GHCR | 新建 GitHub repo 或镜像；保留自建 origin 作为备份 | M0-00 未完成 |
| GHCR 包默认 Private | 服务器 pull 失败 | 改 Public，或服务器 `docker login` | `unauthorized` |
| Docker volume 权限 | SQLite 无法写 | `chown 1000:1000 ./data`；启动日志检查 | `SQLITE_CANTOPEN` |
| WebSocket 被反代断开 | 到账延迟 | Caddy 默认支持；心跳/重连；snapshot 补偿 | 30s 后断线 |
| 移动浏览器音频限制 | 收款人漏提示 | 首次点击解锁；队列；流水兜底 | 无声音 |
| hostToken 丢失 | 房主无法操作 | MVP 接受；文档提示；P1 账号 | 清缓存/换浏览器 |
| SQLite 写竞争 | 付款失败/慢 | 单进程 + `BEGIN IMMEDIATE` + busy_timeout；不并发多副本 | `SQLITE_BUSY` |
| 账本规则漂移 | 余额错误 | `ledger-core` 单一实现 + 重放测试 | 余额与流水不一致 |
| 范围蔓延 | 延期 | P1 backlog；Gate 控制 | 新需求插队 |
| UI 打磨超时 | 延期 | M4 时间盒；先 A 主题，B–F 只换 token | 页面反复改版 |
| 服务器信息未定 | M0 阻塞 | 先本地/临时 IP；上线前确认域名/端口 | 无域名/443 被占 |
| 迁移不可回滚 | 上线失败 | 备份；expand/contract；回滚演练 | 迁移报错 |
